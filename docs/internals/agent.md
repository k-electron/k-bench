# Claude Agent internals

How a [Claude Agent](../../GLOSSARY.md) works inside, and the interfaces each later ticket of the [Claude Agent spec](https://github.com/k-electron/k-bench/issues/128) builds on. The decisions are in [ADR-0007](../adr/0007-agent-runtime-lives-in-a-hidden-tmux-session.md) (where the runtime lives) and [ADR-0008](../adr/0008-the-agent-runtime-holds-the-conversation.md) (who holds the conversation). What the owner sees is in the [guide](../guide/claude-agent.md), and what is done is in the [parity checklist](../claude-agent-parity.md). This page is the map of the code.

```
browser (React)               server (Hono)                       hidden tmux session kb-<session id>
 agentConnection.ts  --WS-->  /api/sessions/:id/agent  --unix-->  Agent Runtime (node, one bundled file)
 agent/transcript.ts   JSON   AgentSockets: relay, unread  lines    |  log.jsonl, the turn, agent.sock
 components/agent/*                                                 `--> installed `claude` (stdio) via the Agent SDK
```

- tmux only keeps the runtime alive and records whether it runs: a tmux session `kb-<id>` exists exactly while the Agent runs, and the reconciler treats it like any other Session (ADR-0001, ADR-0002). **No terminal ever attaches**: `Service.hasRunningShell` is false for an Agent, so the terminal WebSocket closes with 4410.
- The runtime is the single holder of the conversation. The server relays its frames and never parses them.
- The browser turns SDK messages into what is shown (`web/src/agent/transcript.ts`), so a display fix lands on the next page load.

## The wire protocol: `src/shared/agent-protocol.ts`

One definition, imported by the runtime, the server, the browser and the test client; it has no imports and no Node APIs. The same JSON messages travel on the runtime's unix socket (one per line) and on the browser's WebSocket (one per text frame). `AGENT_PROTOCOL_VERSION` is `1`. The protocol **only grows by additions**: a new message `type`, or a new optional field. A receiver ignores a `type` it does not know (`decodeAgentServerMessage` returns `undefined`). A change that cannot be made that way bumps the number.

Runtime to client (`AgentServerMessage`):

| `type`     | Fields                                                                                                | When                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| :--------- | :---------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

The runtime listens only once `claude` has answered the SDK's first request, so `claudeVersion` is always there. `folder` is where Claude Code runs: it names it (`cwd`) only in each turn's `system/init`, so the header has it before the first prompt from here.                                                                                                                                                                                                                                                                                                                                      |
| `status`   | `state`: `"idle"`, `"working"` or `"waiting"`; `turnStartedAt?`; `mode`: the permission mode; `bell?` | On connect, and to every connection whenever it changes ([State](#state-idle-working-waiting-for-you)). `mode` is [the permission mode](#permission-mode). `context` (`AgentContextUsage`: `totalTokens`, `maxTokens`, `percentage`, `autoCompactThreshold?`, `isAutoCompactEnabled`) is what `getContextUsage()` last said: Claude Code does not push it, so the runtime asks at its start and after every turn, and a Claude Code that cannot answer (an older one) only leaves it out. `bell` is [the Agent's Bell](bell.md#a-claude-agents-bell), present only while raised. To **add a message**, add it to the unions here, to the matching `decode...` function, and handle it in `ClientHub` (`src/agent-runtime/hub.ts`, for what concerns the connection) or `command()` in `src/agent-runtime/main.ts` (for what concerns Claude Code). Nothing between the browser and the runtime needs to change: the relay forwards whole frames.

### Log entries (`LogEntry`)

Each is `{seq, t, kind, ...}`; `seq` counts from 1 with no gaps and carries on across runtime restarts. Kinds: `sdk` (`message`: an SDK message **unchanged**, except `stream_event`s), `prompt` (`id`, `text`, `images?`: written before the prompt is sent, because no echo exists until Claude Code takes it up), `runtime` (`event`: `started` or `stopped`, with a `reason`), and `permission_asked` / `permission_answered` (below). A reader ignores a kind it does not know. History never comes from the SDK's `getSessionMessages`, except for the one-time import of Open in web (#156).

### Interrupt and queued prompts

Ticket #138. The owner's controls mid-turn, and what Claude Code does with them.

- **A prompt is never held back.** `prompt` goes to Claude Code at once, whatever it is doing, and Claude Code queues it. k-bench keeps no queue of its own, and the browser keeps none either (see "No connection, no answer" below: a prompt is sent now or not at all, never late). So messages sent mid-turn reach Claude Code in the order sent.
- **Interrupt** is `claude.interrupt()` in `session.ts`, the SDK's `query.interrupt()`: plain, **not** `cancel_queued`. Prompts already queued survive it and run next, in order; that is what "can't be taken back" means, and what the terminal's Esc does with queued input. The turn ends with Claude Code's interrupt shape, logged like any message: an `assistant` message with `aborted: true` holding the text streamed so far, a synthetic `user` message `[Request interrupted by user]` (`... for tool use` when a tool was running), and a `result` with `subtype: "error_during_execution"`. A tool that was running has a `tool_use` and no `tool_result`, which is what shows it red: **#136's tool card must treat a `tool_use` with no result in a turn that has ended as interrupted (red), as well as a `tool_result` with `is_error`**, because which of the two a real interrupt leaves was not recorded. The runtime forwards every `interrupt`, even when it thinks nothing runs (its turn count can be wrong, and an idle Claude Code ignores it). An open permission ask is withdrawn by Claude Code (`cancelled`, see above).
- **"(queued)".** The Transcript shows a prompt as queued from its `prompt` entry until Claude Code says it took it up (`web/src/agent/prompts.ts`, `queuedPromptIds`, from the log alone, so every device agrees). Any one of these ends the wait: a `command_lifecycle` message whose `command_uuid` is the prompt's `id` in a state other than `queued` (`started`, `completed`, `cancelled`); the replayed `user` message with that `uuid`; the `id` in `user_message_uuid` or `user_message_uuids` on any later message; or a `runtime` entry (the runtime that held the prompt is gone). Claude Code sends `queued` the moment a prompt arrives, even when idle, so an idle send shows "(queued)" for an instant.
- **What was recorded and what was not.** Recorded against the real Claude Code (#129): a prompt sent during a text-only reply was **not** folded into it; the reply finished (`result`), then the prompt ran as a turn of its own, `command_lifecycle` `started` marking the start. **A prompt sent during a tool-using turn was not recorded** (it costs real turns, and the build never runs the real `claude`). Claude Code's SDK documentation says a message queued during a turn can be **folded into the running turn between tool rounds**, and then it is named by `user_message_uuids` on the reply frames that follow, and possibly never gets its own `started`. That is why the rule above accepts all the signals instead of relying on `started`; the one-off recording in the next re-record (`scripts/record-fake-claude.ts`, `mid-turn` scenario, with a tool-using prompt) should confirm which fire. If a folded prompt were to send none of them, it would show "(queued)" until the next `runtime` entry.
- Several messages sent close together can be merged by Claude Code into **one turn with one `result`**. The runtime's `status` counts one turn per prompt (`pendingTurns`), so it can read "working" after the merged turn ended; #142 replaces that count with Claude Code's own `session_state_changed`, which fixes it.
- **The browser.** `useAgentConversation` returns `interrupt()`, `interrupting` and `history`. `interrupt()` sends only while the Agent is working, and a second one is refused until a turn has ended since the first: a held Esc repeats, and a second interrupt would stop the queued prompt's turn too. Dropped while reconnecting, like every command. `Composer` shows the `Interrupt` button (square icon, next to Send, on phone and desktop alike) while `state` is `working`, and on desktop Esc in the input does the same. Neither exists while an ask takes over the input (the input is only hidden: Allow/Deny is the way out). Up in an empty input recalls the newest prompt, then older ones (`promptHistory`, from `prompt` entries, a prompt repeated straight away counting once); Down goes back to an empty input. While a recalled prompt is shown, Up and Down step further only when the caret is on its first or last line, and editing it makes it ordinary text. Recall works with any keyboard (an external one on a phone); there is no on-screen control. With #141's paging, history covers the turns that are loaded.

### Permission asks

Where Claude Code would show the terminal's Allow/Deny, it asks the SDK's `canUseTool`, and the runtime (`src/agent-runtime/asks.ts`, `PermissionAsks`, the one place that holds asks) turns that into the protocol below. Later tickets build on this model: #136 shows it in the Transcript, #139 and #142 read it (Waiting is "an ask is open"), #144 closes it at Stop, #146 and #147 replace the card.

- **When Claude asks is the owner's.** k-bench sets no `allowedTools`, no `permissionMode` and no `settings` for it, so Claude Code evaluates the owner's own rules, mode and hooks as in a terminal, and asks the runtime exactly where the terminal would have asked. Nothing in k-bench decides whether to ask.
- **An ask waits as long as the runtime lives**, whoever is connected: no timeout, and no `defer` (which would hand the ask back and end the turn). Closing every tab changes nothing.
- **Asks and answers are log entries.** `permission_asked` is written when Claude asks and holds every field of the SDK's request that can be serialised (`requestId`, `toolName`, `input` as sent, `toolUseId`, `title`, `displayName`, `description`, `blockedPath`, `decisionReason`, `suggestions`, `suppressAlwaysAllowRule`, `defaultToNo`, `agentId`), because the log is permanent: a later ticket cannot add a field to asks already on disk. `permission_answered` (`requestId`, `answer: {decision}`) ends it, **written before Claude Code hears the answer**, so the log reads in the order things happened. `decision` is `allow` or `deny` (the owner's), `cancelled` (Claude Code withdrew the ask: its abort signal fired) or `interrupted` (the runtime stopped, or found at its next start that the previous one had, with the ask open; nobody could ever answer it). Every ask gets exactly one.
- **Open means asked and not answered**, and `openPermissionAsks(entries)` in `agent-protocol.ts` is the one definition, used by the runtime (to close the asks a dead runtime left, at its start, and at `finish()`) and by the browser (to show them). A device that connects, reloads or reconnects therefore sees an open ask from its replay, with no extra message. A `sync` that does not carry the whole log (`tailTurns`, [below](#long-conversations)) still includes every open ask: `AgentLog.readTail` puts the ones from before its start first.
- **Every device is equal; the first answer wins.** `answer {requestId, decision}` goes to the runtime, which looks the ask up. If it is not open, the answer is ignored and nothing is said, not even an `error`: answering on two devices at once is normal. Otherwise the ask is taken out, `permission_answered` is logged and broadcast, and the SDK's promise is resolved. **The card goes only when that entry arrives**, never by a local decision, so the device that answered second loses its card exactly as every other does.
- **The runtime builds the SDK's result.** Allow is `{behavior: "allow", updatedInput: <the ask's own input>, toolUseID}` and Deny is `{behavior: "deny", message, toolUseID}` whose message tells Claude the owner declined, to stop and wait (it comes back as the tool's error). A client says only allow or deny: it can never supply `updatedInput` or `updatedPermissions`. Later answers extend the message by optional fields the runtime turns into the result: `alwaysAllow` (#146: the runtime echoes the `suggestions` it stored), a deny `message` (#146), `answers` for AskUserQuestion and plan feedback (#147). `AskUserQuestion` and `ExitPlanMode` arrive as ordinary asks, so until #147 they show as a bare card.
- **No connection, no answer.** `AgentConnection.send` returns false and drops the message while reconnecting (it is never queued): for an answer that means the card's buttons are disabled, as Send is, and "Reconnecting…" says why. A late Allow, sent after the owner lost the connection and forgot the question, would be worse than a dropped one; after the reconnect the replay shows whether another device answered meanwhile. After a click the buttons stay off until the entry arrives, so a double tap cannot answer twice, and come back if the connection drops first (the answer may not have arrived).
- **Several asks can be open** (a subagent asks while another is). The Pane shows the oldest and says how many wait behind it.
- **A Stopped Agent has no open asks.** `useAgentConversation` returns none once the Session `ended`; #144's Stopped Transcript, which reads the log from disk, must do the same (the runtime closes them as `interrupted` when it exits by itself, and at its next start if it was killed).

### Permission mode

The mode line under the input shows Claude Code's permission mode, and a tap or Shift+Tab switches it (#139). Claude Code owns the mode: the owner's settings start it, plan approval leaves plan mode, a command can change it. So the runtime (`src/agent-runtime/mode.ts`, `PermissionModeTracker`) never assumes it; it takes it from what Claude Code says and publishes it as `status.mode`, to every connection and to every one that connects later, so every device shows the same.

- **Where it comes from:** the `initialize` reply's `current_permission_mode` (so it is known before any turn, and before the runtime listens), each turn's `system/init.permissionMode`, any `system/status.permissionMode` (how Claude Code reports a change it makes itself), and a switch Claude Code accepted. A mode change appears only in `status`, not in the log: it is a state, not part of the conversation.
- **Switching:** `set_permission_mode {mode}` calls the SDK's `setPermissionMode`. The client sends the **target** (the next mode after the one it shows, `nextPermissionMode`), not "next", so two devices tapping at once ask for the same mode and it is set once. The line changes only when the runtime's `status` arrives, never by a local guess. If Claude Code refuses, nothing changes and nothing is said.
- **The cycle** is `PERMISSION_MODE_CYCLE` in `agent-protocol.ts`: Ask before edits (`default`), Accept edits, Plan mode. The runtime accepts nothing else from a client, so no client can switch on `bypassPermissions` (it needs an opt-in made outside k-bench). **Unverified:** the TUI also offers `auto` in its cycle where it is enabled, and nothing tells k-bench whether it is; adding it is one line in `PERMISSION_MODE_CYCLE` once there is a way to know. A mode outside the cycle (the owner's settings started Claude Code in `auto`) is shown, and the next switch goes to `default`.
- **The browser:** `ModeLine` (a button named `Permission mode`) under `Composer`, which takes Shift+Tab on desktop (`onShiftTab`, with `preventDefault` so the focus stays in the box). Both call `cycleMode()` from `useAgentConversation`. Disabled while reconnecting or ended, as Send is.

## State: Idle, Working, Waiting for you

What an Agent is doing is one word in `status.state`, which the runtime decides (`src/agent-runtime/activity.ts`, `Activity`) and pushes to every connection whenever it changes:

- **Waiting** is `PermissionAsks.count > 0`: an ask is open. It wins over Working.
- **Working** is a turn running, **whoever started it**. A prompt k-bench sent counts from the moment it is sent, until its `result`, so there is no Idle gap between a turn and the prompt queued behind it. A turn nobody sent (`/loop`) is seen from Claude Code's messages: the first `system/init`, `stream_event`, `assistant`, `user` or `tool_progress` after Idle starts it, and the `result` ends it. A late `system` message after a `result` (a hook, a background task) does not start one.
- **Idle** is neither.
- `turnStartedAt` (the runtime's clock, which is the Host's) is set when the Agent leaves Idle and kept through Working and Waiting, so "Working · 42s" is the turn's time, not the wait's. It is absent when Idle.
- `bell` is not a state but rides on the same `status`: the Agent's Bell, held by the runtime (`AgentBell`) and cleared by a `view {visible: true}` from any connection. How it works is in [Bell](bell.md#a-claude-agents-bell). `AgentStatuses.bellOf` hands it to `Service.getState`, which uses it as `SessionState.bell` for an Agent in place of tmux's.

Claude Code is also asked to report it itself (`CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1` in the environment the SDK gives `claude`, the owner's own plus that one): `system/session_state_changed` (`running`, `requires_action`, `idle`). When it comes it is believed (`idle` ends the turn and clears every counted prompt). **It is not relied on**: whether the real Claude Code sends it for a turn nobody sent has not been confirmed, so the message-based rule above carries the state alone (the fake can be told never to send it with `configure({ sessionStateMessages: false })`, and `test/claude-agent-state.test.ts` covers a turn nobody sent both ways). A command that takes no turn must not leave a prompt counted for ever: `conversation_reset` and Claude Code's `idle` clear the count as well as `result` lowers it.

The server (`src/server/agent-status.ts`, `AgentStatuses`) keeps **one status connection per running runtime**, opened with `AgentRuntimes.connect`. It never sends `sync`, so it receives only `hello` and `status`, and it keeps the last of each in memory: a cache of what the runtime said, dropped when the connection drops or the Agent stops running, never stored. `Service.getState()` is what starts and ends the watching: each read already asks tmux which Sessions live, and tells `AgentStatuses.follow` which of the Claude Agents among them run, so a new Agent, a restarted one and every Agent after a k-bench restart are picked up the same way. At startup `startServer` waits (up to three seconds) for what each running Agent says before the first state is read (`Service.watchAgents`), so a client never sees an Agent that was Working shown as anything else. Every change calls `feed.notify()`, so it reaches the events socket at once. The state is `SessionState.agent` (`src/shared/state-protocol.ts`: `state`, `turnStartedAt`, and the `claudeVersion` and `runtimeBuildId` from the hello); an Agent with no status heard yet has no `agent` and is shown like any running Session. Stopped is not a runtime state: it is the Session's `status`.

The browser (`web/src/agentState.ts`) turns that into the four things shown: the dot and row edge in `SessionRow` (green dot and faint edge for Idle; spinning green ring and green edge for Working; pulsing orange for Waiting for you, with `row-waiting` beside `row-pulse` so that orange wins on a row that has both; hollow and no edge for Stopped), a collapsed `WorkspaceRow` that turns orange while any Agent in it waits, and the top bar's `● Idle`, `◌ Working · 42s`, `● Waiting for you`, `○ Stopped` in `PaneLabels`. The seconds count from `turnStartedAt` on the browser's clock, so a device whose clock is wrong shows them wrong. The dot's accessible name is `<name> idle`, `working`, `waiting for you` or `stopped`; a Waiting row also carries a `role=status` text `<name> is waiting for you` (and a collapsed Workspace `<name> has an agent waiting for you`), which is what tests look for, as the pulse is animation.

## Long conversations

A page opens on the latest turns, not the whole log, and the owner scrolls up for the rest (#141).

- **A turn** (`turnStarts` in `src/agent/log.ts`) runs from a prompt that follows a `result` (or the log's start) to the next such prompt; for a turn nobody sent, Claude Code's `system/init` stands in for the prompt. Whatever Claude Code says after a `result` (the Session going idle, a command completing) belongs to the turn that ended, and a prompt sent while a reply streams belongs to the turn it was sent in. So a turn is never cut between a `tool_use` and its `tool_result`, a message that is mid-stream is always in the tail, and a page boundary is always a turn boundary. What a later ticket's reducer needs of a turn's start (the header's `system/init`, a prompt's echo) is in the tail with it.
- **Fresh load.** The browser's first `sync` is `{afterSeq: 0, tailTurns: 5}` (`agentConnection.ts`; it is `afterSeq: lastSeq` with no `tailTurns` on every reconnect, so a connection never has a gap). The runtime answers with `AgentLog.readTail`: from the start of the fifth-last turn to the end, plus any open ask from before it, and `from` says where the range starts. `snapshot`, live entries and fragments are as before, because the message streaming now is always in the tail.
- **Scrolling up.** `page {beforeSeq, limit: 20}` with `beforeSeq` the `from` the browser holds, answered by `AgentLog.readPage` with the `limit` turns before it. The page's `from` becomes the next `beforeSeq`, so pages meet exactly, until `from` is 1. The reducer (`transcript.ts`) keeps `earliestSeq`, merges a page ahead of the entries held by `seq` (an ask already held is not added twice), and ignores a page that reaches no further back than what is held. `permissionAsks` and the snapshot's block count read `state.entries`, so they agree with a tail-only state.
- **The Pane** (`components/agent/useScrollBack.ts`) watches a sentinel at the top of the conversation with an `IntersectionObserver` (200px early), asks for a page when it shows and there is more, looks again after each page (a conversation still too short to scroll keeps loading until it is not), and moves the scroll position by the height a page adds above, in the same frame, so what the owner reads does not move. The scroller sets `overflow-anchor: none`: Safari has no scroll anchoring and two corrections must not both act. A request in flight is forgotten when the connection drops, and made again once it is back.
- **Old runtimes.** A runtime built before this ignores `tailTurns` and replies with no `from`, which the browser reads as 1: the whole log, nothing to page.

### Images

Showing Claude a screenshot (#159; this follows a default not yet confirmed with the owner). **Names go over the socket, bytes go over HTTP.**

- The browser checks an image against Claude's limits (`src/shared/agent-images.ts`: PNG, JPEG, GIF or WebP; **5 MiB measured on the base64 text**, as Claude measures it, so about 3.9 MB of file; 8000 pixels on the longest edge, which only the browser can count; 20 per message) and, if it passes, uploads it **at once** (`POST /api/sessions/:id/agent/images`, base64 inside JSON, so the `application/json` check stays a second line behind the Origin check; [API](api.md)). One that fails is never uploaded. Uploading at attach time keeps Send as quick with images as without; the cost is that an image attached and then removed stays on disk until the Session is deleted.
- The server checks type, size and the file's first bytes again, stores it as `<agent folder>/images/<uuid>.<ext>` (mode `0600`; `images/` is made without recursion, so an upload racing a delete fails instead of bringing the Agent's folder back) and answers its name.
- The `prompt` carries the names. The protocol accepts only `<uuid>.<ext>` names (`STORED_IMAGE_NAME`), so a client cannot make the runtime read another file. The runtime (`src/agent-runtime/images.ts`, `promptContent`) builds the SDK message's `content`: an image block `{type: "image", source: {type: "base64", media_type, data}}` per image, then a text block if there is text; with no images `content` stays the plain string. It does this **before** logging or counting the prompt, and a file that cannot be read becomes a short text note rather than an error, so a lost image never takes the Agent down. The log's `prompt` entry keeps the names, never the bytes.
- The conversation shows the images of a prompt above its text (`PromptImages`, from `GET .../agent/images/:name`). Deleting the Session removes the Agent folder, and the images with it.
- Browser: `web/src/agent/images.ts` (the checks), `useAttachments.ts` (state, upload) and `components/agent/Attachments.tsx` (thumbnails, the `Attach image` button, whose `accept="image/*"` input is the photo library on a phone). Accessible names: the button `Attach image`, the list `Attached images` of thumbnails `Attached: <file name>` each with a button `Remove <file name>`, the over-limit message a `role=alert`, and the sent images `Your attachment` in the list `Images sent`.

## The Agent folder: `src/agent/`

Node code shared by the server (which compiles it, `tsconfig.build.json`) and the runtime (which bundles it). It must never import from `src/server` or `src/agent-runtime`.

- `paths.ts`: every location, so the two sides cannot disagree. `<dataDir>/agents/<session id>/` holds `log.jsonl`, `agent.sock` and `exit.json` and `images/` (#159). `<dataDir>/runtimes/<build id>/agent-runtime.mjs` is an installed runtime. `agentsRoot`, `agentFolder`, `agentImagesFolder`, `agentLogFile`, `agentSocketFile`, `agentExitFile`, `runtimeFile`, `runtimeBuildId(bytes)` (SHA-256 hex), `makeOwnerOnlyFolder` and `ensureOwnerOnlyFolder`.
- **Permissions.** The parent and each Agent folder are mode `0700`, set with `chmod` after `mkdir` because the umask cuts `mkdir`'s own mode. There is no token: whoever can open the folder can reach the socket. Node binds a unix socket path longer than macOS's 104 bytes (checked to 250 characters, so no short-path trick is needed; do not try it with `nc -U`); a data folder so deep that the path passes about 255 makes the Agent fail to start, with the reason. **Only the server creates these folders.** The runtime and the launcher never `mkdir`, so a runtime still exiting cannot bring back a folder the server just deleted.
- `log.ts`: `AgentLog(file)` with `append(entry)` (numbers and stamps it, `appendFileSync`), `readAfter(seq)`, `readTail(turns)`, `readPage(beforeSeq, turns)`, `last` and `hasPrompt()`, and `turnStarts(entries)` (what a turn is, [below](#long-conversations)). A write cut short by a crash is skipped on read. The runtime appends and the server reads it directly while an Agent is Stopped (#144), so both show the same history, and #144's Stopped Transcript opens with `readTail` and pages with `readPage` exactly as the runtime does.
- `exit.ts`: `exit.json` (`{reason?, code?, signal?, at}`). tmux ends a Session's pane, and so the Session, the moment its command exits, so this file is the only place a reason survives. The runtime writes it with a reason in plain words on every exit it controls (Claude Code died, shut down, a signal, a crash); the launcher fills the gap when the runtime was killed (`code`, `signal`, no `reason`). Readers: `readExitRecord(folder)`. The launcher deletes it before each start.
- `lines.ts`: `LineSplitter`, the newline framing of the unix socket.

## The Agent Runtime: `src/agent-runtime/`

One long-lived Node process per Agent, started with `--agent-dir --folder --claude --conversation --mode` (`args.ts`; arguments only, never environment, because the tmux server's environment is whatever its first command had). `main.ts` wires:

- `session.ts`, `ClaudeSession`: the Agent SDK's `query()` pointed at the owner's installed `claude` (`pathToClaudeCodeExecutable`, absolute) with everything the spec fixes: the `claude_code` system prompt preset, the default settings sources (`settingSources` left unset, so CLAUDE.md, skills, plugins, hooks, MCP servers and permission rules load as in the terminal), `includePartialMessages`, **`enableFileCheckpointing: true` from the first launch** (it cannot be added later, and `/rewind` in the terminal depends on it), `extraArgs: {"replay-user-messages": null}`, and the `canUseTool` the runtime hands it (`PermissionAsks`, [below](#permission-asks): it waits for as long as the runtime lives, there is no `defer`). `mode: "start"` is `sessionId` (`--session-id=`); `mode: "resume"` is `resume` (`--resume=`), except that when the log holds no prompt it starts instead, because Claude Code saves a conversation only after its first message.
- `asks.ts`, `PermissionAsks`: the permission asks Claude Code has made and nobody has answered: the `canUseTool` it hands the session, `answer()`, and the entries they write ([Permission asks](#permission-asks)).
- `hub.ts`, `ClientHub`: the unix socket (mode `0600` inside a `0700` folder), a hello for each connection, validation, `sync`, and the fan-out of entries and fragments. It knows nothing of Claude Code.
- `live.ts`, `LiveText`: the text so far of the message now streaming (by content block), fed by `main.ts` with every fragment and cleared on `message_stop` and on a `result`. It is what the hub sends as the `snapshot`. Subagent fragments are not kept, as the browser never shows them live.
- `main.ts`: logs every SDK message (`record()`: append, then send to every synced connection, so order is preserved), asks `getContextUsage()` at its start and after every turn for `status.context` (`ClaudeSession.contextUsage()`; a failure, from an older Claude Code or one going away, is caught and only leaves it out, never ending the Agent), and ends:
  - **Shutdown** (the `shutdown` command, or SIGTERM, SIGHUP, SIGINT): records a `runtime stopped` entry and `exit.json`, closes Claude Code (`query.close()` kills it) and the socket, exits 0. The server kills the tmux session if the runtime has not exited a few seconds after `shutdown` (`AgentRuntimes.shutdown`).
  - **Claude Code ended or the runtime failed**: the same, with the reason, and exit status 1. Nothing restarts it. Claude Code and the runtime live and die together.
- It listens only once `claude` has said which version it is (`initializationResult()`), so every hello carries `claudeVersion`.

### The build and the build ID

`vite.runtime.config.ts` builds `src/agent-runtime/main.ts` into **one self-contained file**, `dist/runtime/agent-runtime.mjs`, with the Agent SDK inside (`build.ssr`, `ssr.noExternal`, one chunk), about 1.4 MB, run by plain `node`. `pnpm build:runtime` builds it and `pnpm build` includes it. The SDK is a development dependency only (pinned exactly; Dependabot gives it its own pull request), so the published package depends on no SDK, and installing k-bench never fetches the SDK's optional platform package with its bundled Claude Code (about 338 MB). The SDK's own version (`sdkVersion`) and the Claude Code version it was made for (`sdkClaudeCodeVersion`) are baked in with Vite's `define`, because the SDK is not installed where the runtime runs. **The runtime build ID is the SHA-256 of the file**; the runtime computes it from its own bytes, since a file cannot hold its own hash.

Note for whoever reviews dependencies: the bundle contains the SDK's code, which has its own license ("SEE LICENSE IN README.md" in its package), not k-bench's MIT.

### Launching: `agentCommand` in `src/server/claude.ts`

`TmuxDriver.createAgentSession(id, folder, launch)` starts the runtime as the Session's only program. The command is the same three-hop chain as a Claude TUI (`loginChain`): zsh with no startup files changes into the folder, the owner's login shell (`-l -i`) gives the owner's environment, and `/bin/sh` runs the Agent launcher with positional arguments only (never spliced into script text). The launcher resolves `claude` with `command -v` inside the login shell (the SDK needs an absolute path; a name with a slash is used as given), then **runs Node as a child, not with `exec`**, so it outlives the runtime and writes the `exit.json` gap record for an exit the runtime did not record. It is POSIX `sh`, so it runs under macOS's bash-as-sh and CI.

## The server

- `src/server/agents.ts`, **`AgentRuntimes`**: everything the server does to an Agent. It keeps no state about a running Agent (tmux says what runs):
  - `install()`: copies the built runtime into `<dataDir>/runtimes/<build id>/` (once; content-addressed; through a temporary name), so a running runtime survives the app folder being replaced by an update (ADR-0007). It never throws: without a runtime only Claude Agents are unavailable (`current`, and `launch` says why). Keeping the folder until no running runtime uses it is #158.
  - `launch({sessionId, workspaceFolder, conversationId, mode})`: makes the Agent's folder (`0700`) and starts the runtime.
  - `connect(sessionId, stillWanted)`: the runtime's socket, retried until it listens; used by the relay and by the status connections (`AgentStatuses`, [State](#state-idle-working-waiting-for-you)).
  - `waitUntilReady(sessionId)`: the runtime's hello, or an `AgentStartError` carrying the reason it recorded. Creating an Agent waits for it, so the API answers once the Agent is running, and a failed start leaves no Session, tmux session or folder.
  - `isRunning`, `shutdown(sessionId)` (send `shutdown`, wait for the tmux session to go, kill it after four seconds), `removeFolder`.
- `src/server/agent-sockets.ts`, **`AgentSockets`**: `GET /api/sessions/:id/agent`, behind the same access guard and Origin check as the terminal (`server.on("upgrade")` in `server.ts`). For each browser socket it opens one connection to the runtime's socket and forwards whole frames both ways unread. It closes with **4410** only when the Session ended (not a running Agent when asked, or the runtime hung up and its tmux session went); a runtime that hung up while its Session is still running, or one that did not start, closes with 1011; a stopping server drops the socket with no 4410 so that the browser reconnects (#134).
- `service.ts`: `createSession(workspaceId, name, claude?: {options, interface})`; Claude Agent is `interface: "agent"`. Delete (of a Session or a Workspace) shuts the runtime down, removes the row, then removes the folder. Restart of a Stopped Agent starts the runtime with `mode: "resume"` (#144 extends it: Stop, the Stopped Transcript, confirms). `getState()` adds `interface` for Claude Sessions.
- `store.ts`: `sessions.interface` (`tui` or `agent`, null for a shell; existing Claude Sessions became `tui`). The New Session dialog's remembered kind can be `claude-agent`; creating an Agent leaves the remembered Launch options as they were.
- `config.ts` / `ServerOptions.agentRuntimeFile`: the built runtime to install. `main.ts` passes `dist/runtime/agent-runtime.mjs` relative to its working directory, as it does `dist/web`. It is an option, not an instance setting, so a test can start a server on a second runtime build (#158).

## The browser

- `web/src/agentConnection.ts`: `createAgentConnection({sessionId, openSocket})`, no React: opens the socket and keeps it open, the same shape as `terminalConnection.ts`: when it drops it reconnects with backoff (`retryFirstMs` 500, doubling to `retryMaxMs` 5000), and at once when `wake` fires (the page became visible, the browser went online: `retryWhenAwake`). Every socket it opens starts with `sync` from the newest entry it has had (`lastSeq`), so across any number of drops the listener gets each entry once. It reports `message`, `reconnecting(on)` and `ended` (a close with 4410, never retried). `send` returns whether the command was sent or kept: while reconnecting it is dropped, never queued, so a prompt cannot go out late; the Composer disables Send and keeps the text meanwhile, and the Pane says "Reconnecting…". Closing a tab, a device sleeping and k-bench restarting only end a connection: the runtime never notices.
- `web/src/agent/transcript.ts`: what the conversation holds, and how messages go in: `applyServerMessage(state, message)` keeps the log entries and the live fragments, and `transcriptItems(state)` gives the items to show (what `buildItems` makes of the entries, then the streaming ones). Partial text is shown until the complete message for its block arrives (Claude Code sends one complete `assistant` message per content block, in order), and replaced by it. A `replay` clears the streamed text the state holds and a `snapshot` sets it, counting the blocks of that message the replay already held complete, so a joiner never sees a block twice. `permissionAsks(state)` gives the open asks as `PermissionAsk` view-models (the log entry without its numbering; defined in #135, extended by #146 and #147), derived from the entries alone. `transcriptInfo(state)` gives the model and folder of the latest turn, for the header.
- `web/src/agent/items.ts`, `toolDisplay.ts`, `activity.ts`: the Transcript's rendering rules, [below](#the-transcript).
- `web/src/agent/useAgentConversation.ts`: the hook the Pane uses: `{items, entries, asks, header, hello, state, mode, turnStartedAt, context, ended, reconnecting, send, answer, cycleMode, interrupt, interrupting, history}`.
- `web/src/components/agent/`: `AgentPane` (the header, the conversation, `role=log`, the status line), `Transcript` (the items, each in a `RawMessage`), `AgentHeader`, `StatusLine`, `PromptDock` (what is under it: the input, or, while Claude waits on an ask, `PermissionPrompt`, the bare Allow/Deny card, with the input only hidden so a half-typed message survives), `Composer` (the input). On desktop Enter sends and Shift+Enter starts a new line; on a phone Return starts a new line and the Send button sends. A Claude Agent never gets Extra keys or Smart typing (`usePaneView.focusedHasTerminal`). `Pane.tsx` switches on `session.kind === "claude" && session.interface === "agent"`; `SessionRow` shows a speech bubble and keeps the Claude spark.
- Accessible names tests across tickets rely on (keep them stable): the Pane region `Claude Agent <name>`, the conversation `Conversation` (`role=log`), the input `Message Claude`, the buttons `Send` and `Interrupt` (the latter only while Claude works), the permission card, a region `Permission prompt` with the buttons `Allow` and `Deny` (#146 keeps the region and renames the buttons to its numbered choices), the dialog kind `Claude Agent (WIP)`, the checkbox `Raw`, the desktop button `Show raw message` (`Hide raw message` while open) and the raw JSON `Raw message` (one message) or `Raw message <seq>` (the whole Transcript).

### The raw view (#137) and its seam

The raw JSON of any message is the fallback whenever something renders wrongly, and the place an Unsupported row (#153) sends the owner. It is browser-only and holds nothing but display state.

- **What "raw" is** (`web/src/agent/raw.ts`, `rawOf(entry)`): for an `sdk` log entry, the SDK message **exactly as Claude Code sent it**, with no `seq`/`t`/`kind` wrapper (the runtime logs it unchanged, so this is the original, indented for reading). For any other kind (`prompt`, `permission_asked`, `runtime`...), k-bench's own record, which is the entry itself. Live `stream_event` fragments are never logged and have no raw.
- **The seam is the entry's `seq`.** Every `TranscriptItem` built from a log entry carries that entry's `seq` (`item.seq`; text still streaming has none). A new item kind (#136's reshaped items, #148, #153...) **must set `seq`** from the entry it comes from, or its message offers no raw. A row built from several entries sets the one the owner would call "the message". `useAgentConversation` returns `entries` (the log entries received) so the Pane can find the entry of an item.
- **The UI** is `components/agent/RawView.tsx`. `useRawView()` holds the choices for this device (`all`, `isShown(seq)`, `show(seq)`, `toggle(seq)`); `RawMessage` wraps a row and adds `</>` on desktop (on hover or keyboard focus) or a long-press on a phone (a touch held 500 ms without drifting 10 px, so a scroll or a tap is not one), which shows the JSON under the row and, again, hides it; `RawSwitch` is the header's `Raw` checkbox; with it on, `RawTranscript` replaces the conversation with every entry's JSON in order, including entries no row shows, and off brings the conversation back.
- **An Unsupported row opens it** with `useShowRaw()(item.seq)`, the `onShowRaw` of the spec; `AgentPane` provides it (`ShowRawProvider`) around the conversation's rows. It shows that message's raw JSON under the row, the same as the `</>`. A row that renders several blocks of one entry shows the JSON under each block of it.

## The Transcript

The conversation in Claude TUI's shape ([#136](https://github.com/k-electron/k-bench/issues/136)). The browser makes it from the raw SDK messages in the log, every time, so a display fix reaches even a long-running Agent on the next page load. Later tickets add to it by the seams below, in new files rather than by growing these.

- **Entries to items: `buildItems(entries)` in `web/src/agent/items.ts`.** Pure, one pass over the log. The items (`TranscriptItem`, a union on `kind`): `prompt` (`>` in a band, with `(queued)` until Claude Code has picked it up: `prompts.ts`, #138), `assistant` (`⏺` and markdown), `thinking` (one muted line, with its duration from the frame's `thinking_duration_ms`), `tool` (`⏺ Name(target)` and its result under `⎿`) and `interrupted` (`⎿ Interrupted`). Each carries a stable `key` and, unless it is still streaming, the `seq` of the entry it came from (what the Raw view, #137, shows for it: `Transcript` wraps every item in a `RawMessage`). **To show a new kind of thing:** add its interface and put it in the union; make it in `buildItems` (`readSdkMessage` for an SDK message, the switch for the other kinds of entry); add a case in `TranscriptItemView` (`components/agent/Transcript.tsx`), where a `never` check fails to compile until there is one. A message type `buildItems` does not read shows nothing yet: #148, #149, #152 and #153 each give theirs a line, and #153 makes the rest visible as Unsupported.
- **What the rules are.** A prompt k-bench sent is shown from its `prompt` entry (there is no echo until Claude Code picks it up), and the echo with the same `uuid` is not shown again; an echo k-bench did not send (typed in the terminal, imported) is shown as a prompt. A tool call is paired with its `tool_result` by `tool_use_id`: no result yet is **running** (a spinner), a result is **done** (green), and red is **denied** (the owner's `deny` in the log, or Claude Code's `permission_decision` of `reject`), **interrupted** (Claude Code says so in the result, or the turn's `result` message, or a runtime start or stop, came with the call still without one) or **failed** (`is_error`). A call that was interrupted has no result line of its own, only the red mark: the `Interrupted` line the interrupt leaves says it once. Subagent messages (`parent_tool_use_id`) are left to #149.
- **Tool wording: `web/src/agent/toolDisplay.ts`.** `toolTarget` (the part in parentheses: a Bash command, a path relative to the turn's `cwd`, a pattern, a URL), `toolDisplayName` (an MCP tool as `server - tool (MCP)`), `toolDiff` (an edit's lines, from Claude Code's `structuredPatch` when its result has one, else from the input's `old_string`/`new_string`, a `Write`'s content as added lines), `toolResultView` (the `⎿` summary and output lines). They take only the tool's input where they can, so the permission panel (#146) can show the same target and diff before the tool has run. A tool not named there gets the generic reading, so a new Claude Code tool still shows.
- **Components, one per concern:** `Transcript` and `TranscriptItemView` (the switch), `ToolCall` (status mark, result, diff), `Markdown` (react-markdown with GitHub tables and task lists, no raw HTML; a development dependency, bundled into `dist/web`), `Diff` (`<ins>` and `<del>` lines, scrolling sideways inside its box), `ExpandableLines` (the collapse: five lines of output, twenty of a diff, "+N lines, tap to expand"; reuse it for any long run of lines), `AgentHeader`, `StatusLine`. Items and their components are memoised, and `transcriptItems` rebuilds the log's items only when entries arrive, so a stream of fragments re-renders only what is streaming.
- **Header and status line.** The header is `claude <version> · <model> · <folder>`: the version from `hello`, the model from the latest `system/init`, and the folder from `init.cwd`, or `hello.folder` before it. Claude Code sends `system/init` at the start of **every turn**, not at process start, so before the first prompt the model is left out. The status line shows `✻ <activity>… (<n>s)` while the Agent is Working (`status.state`, `turnStartedAt`; activity is read from the end of the items by `currentActivity`), `✻ Waiting for you (<n>s)` while it is Waiting, and goes when the turn ends. It also shows `Context left until auto-compact: N%` whenever Claude Code has reported it, because that is what is glanced at between turns. The percentage is worked out in the browser (`contextLeftPercent`: what is left of `autoCompactThreshold`, read as tokens, after `totalTokens`), so if that reading is wrong the fix is a display fix. `turnStartedAt` is the runtime's clock: the seconds are clamped at zero, and a device whose clock differs from the Host's shows them off by the difference.
- **Accessible names** (keep them stable; tests across tickets use them): the header `note` "Claude Code"; each item an `article`: "Your prompt", "Claude", "Thinking", and for a tool "`Name(target)`"; the tool's state an `img` named "Running", "Done", "Denied", "Interrupted" or "Failed"; an edit's diff a `figure` "Diff of `target`" with `insertion` and `deletion` lines; the expand button "+N lines, tap to expand" (then "Show fewer lines"; `aria-expanded`); the status line a `status` "Claude status", and the context a `note` "Context left". The glyphs (`>`, `⏺`, `⎿`, `✻`) are `aria-hidden`.
