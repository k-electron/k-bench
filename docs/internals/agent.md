# Claude Agent internals

How a [Claude Agent](../../GLOSSARY.md) works inside, and the interfaces each later ticket of the [Claude Agent spec](https://github.com/k-electron/k-bench/issues/128) builds on. The decisions are in [ADR-0007](../adr/0007-agent-runtime-lives-in-a-hidden-tmux-session.md) (where the runtime lives) and [ADR-0008](../adr/0008-the-agent-runtime-holds-the-conversation.md) (who holds the conversation). What the owner sees is in the [guide](../guide/claude-agent.md), and what is done is in the [parity checklist](../claude-agent-parity.md). This page is the map of the code.

```
browser (React)               server (Hono)                       hidden tmux session kb-<session id>
 agentConnection.ts  --WS-->  /api/sessions/:id/agent  --unix-->  Agent Runtime (node, one bundled file)
 agent/transcript.ts   JSON   AgentSockets: relay, unread  lines    |  log.jsonl, the turn, agent.sock
 components/agent/*                                                 `--> installed `claude` (stdio) via the Agent SDK
```

- tmux only keeps the runtime alive and records whether it runs: a tmux session `kb-<id>` exists exactly while the Agent runs, and the reconciler treats it like any other Session (ADR-0001, ADR-0002). **No terminal ever attaches**: `Service.hasRunningShell` is false for an Agent, so the terminal WebSocket closes with 4410.
- The runtime is the single holder of the conversation. The server relays its frames and never parses them.
- The browser turns SDK messages into what is shown (`web/src/agent/transcript.ts`), so a display fix lands on the next page load.

## The wire protocol: `src/shared/agent-protocol.ts`

One definition, imported by the runtime, the server, the browser and the test client; it has no imports and no Node APIs. The same JSON messages travel on the runtime's unix socket (one per line) and on the browser's WebSocket (one per text frame). `AGENT_PROTOCOL_VERSION` is `1`. The protocol **only grows by additions**: a new message `type`, or a new optional field. A receiver ignores a `type` it does not know (`decodeAgentServerMessage` returns `undefined`). A change that cannot be made that way bumps the number.

Nothing between the browser and the runtime needs to change: the relay forwards whole frames.

### Log entries (`LogEntry`)

Each is `{seq, t, kind, ...}`; `seq` counts from 1 with no gaps and carries on across runtime restarts. Kinds: `sdk` (`message`: an SDK message **unchanged**, except `stream_event`s), `prompt` (`id`, `text`, `images?`: written before the prompt is sent, because no echo exists until Claude Code takes it up), `runtime` (`event`: `started` or `stopped`, with a `reason`), `divider` (`label`: a line between turns that is not a message, written only by Open in web's import), `declined` (a request the runtime declined for the owner, [Unsupported](#unsupported-rows): `what` is `elicitation`, `request` what the SDK handed over), and `permission_asked` / `permission_answered` (below). A reader ignores a kind it does not know. History never comes from the SDK's `getSessionMessages`, except for the one-time import of Open in web (#156).

### Interrupt and queued prompts

Ticket #138. The owner's controls mid-turn, and what Claude Code does with them.

- **A prompt is never held back.** `prompt` goes to Claude Code at once, whatever it is doing, and Claude Code queues it. k-bench keeps no queue of its own, and the browser keeps none either (see "No connection, no answer" below: a prompt is sent now or not at all, never late). So messages sent mid-turn reach Claude Code in the order sent.
- **Interrupt** is `claude.interrupt()` in `session.ts`, the SDK's `query.interrupt()`: plain, **not** `cancel_queued`. Prompts already queued survive it and run next, in order; that is what "can't be taken back" means, and what the terminal's Esc does with queued input. The turn ends with Claude Code's interrupt shape, logged like any message: an `assistant` message with `aborted: true` holding the text streamed so far, a synthetic `user` message `[Request interrupted by user]` (`... for tool use` when a tool was running), and a `result` with `subtype: "error_during_execution"`. A tool that was running has a `tool_use` and no `tool_result`, which is what shows it red: **#136's tool card must treat a `tool_use` with no result in a turn that has ended as interrupted (red), as well as a `tool_result` with `is_error`**, because which of the two a real interrupt leaves was not recorded. The runtime forwards every `interrupt`, even when it thinks nothing runs (its turn count can be wrong, and an idle Claude Code ignores it). An open permission ask is withdrawn by Claude Code (`cancelled`, see above). **Background subagents and tasks survive an interrupt**: the runtime declares `perTaskStopAffordance` to Claude Code (every task line has its own Stop), which is what makes Claude Code spare them; without it an interrupt kills them all. A task that blocks its turn ends with it.
- **"(queued)".** The Transcript shows a prompt as queued from its `prompt` entry until Claude Code says it took it up (`web/src/agent/prompts.ts`, `queuedPromptIds`, from the log alone, so every device agrees). Any one of these ends the wait: a `command_lifecycle` message whose `command_uuid` is the prompt's `id` in a state other than `queued` (`started`, `completed`, `cancelled`); the replayed `user` message with that `uuid`; the `id` in `user_message_uuid` or `user_message_uuids` on any later message; or a `runtime` entry (the runtime that held the prompt is gone). Claude Code sends `queued` the moment a prompt arrives, even when idle, so an idle send shows "(queued)" for an instant.
- **What was recorded and what was not.** Recorded against the real Claude Code (#129): a prompt sent during a text-only reply was **not** folded into it; the reply finished (`result`), then the prompt ran as a turn of its own, `command_lifecycle` `started` marking the start. **A prompt sent during a tool-using turn** was recorded by the live check (#161): Claude Code **folded it into the running turn** between tool rounds. It sent `command_lifecycle` `queued` at once; then, between two tool rounds, the replayed `user` echo of the prompt and `command_lifecycle` `started`; `user_message_uuids` named it on the following `status` frames and on the `result`; there was **one `result` for both prompts**, and `completed` for each (the second's before the `result`). Every signal the rule above accepts came, so "(queued)" cleared and nothing needs changing. Because of the shared `result`, the live check ends a prompt at its `completed`, not at a `result`.
- Several messages sent close together can be merged by Claude Code into **one turn with one `result`**. The runtime's `status` counts one turn per prompt (`pendingTurns`), so it can read "working" after the merged turn ended; #142 replaces that count with Claude Code's own `session_state_changed`, which fixes it.
- **The browser.** `useAgentConversation` returns `interrupt()`, `interrupting` and `history`. `interrupt()` sends only while the Agent is working, and a second one is refused until a turn has ended since the first: a held Esc repeats, and a second interrupt would stop the queued prompt's turn too. Dropped while reconnecting, like every command. `Composer` shows the `Interrupt` button (square icon, next to Send, on phone and desktop alike) while `state` is `working`, and on desktop Esc in the input does the same. Neither exists while an ask takes over the input (the input is only hidden: Allow/Deny is the way out). Up in an empty input recalls the newest prompt, then older ones (`promptHistory`, from `prompt` entries, a prompt repeated straight away counting once); Down goes back to an empty input. While a recalled prompt is shown, Up and Down step further only when the caret is on its first or last line, and editing it makes it ordinary text. Recall works with any keyboard (an external one on a phone); there is no on-screen control. With #141's paging, history covers the turns that are loaded.

### Permission asks

Where Claude Code would show the terminal's Allow/Deny, it asks the SDK's `canUseTool`, and the runtime (`src/agent-runtime/asks.ts`, `PermissionAsks`, the one place that holds asks) turns that into the protocol below. Later tickets build on this model: #136 shows it in the Transcript, #139 and #142 read it (Waiting is "an ask is open"), #144 closes it at Stop, #146 gave it the docked panel and #147 adds the question and plan panels.

- **When Claude asks is the owner's.** k-bench sets no `allowedTools`, no `permissionMode` and no `settings` for it, so Claude Code evaluates the owner's own rules, mode and hooks as in a terminal, and asks the runtime exactly where the terminal would have asked. Nothing in k-bench decides whether to ask.
- **An ask waits as long as the runtime lives**, whoever is connected: no timeout, and no `defer` (which would hand the ask back and end the turn). Closing every tab changes nothing.
- **Asks and answers are log entries.** `permission_asked` is written when Claude asks and holds every field of the SDK's request that can be serialised (`requestId`, `toolName`, `input` as sent, `toolUseId`, `title`, `displayName`, `description`, `blockedPath`, `decisionReason`, `suggestions`, `suppressAlwaysAllowRule`, `defaultToNo`, `agentId`), because the log is permanent: a later ticket cannot add a field to asks already on disk. `permission_answered` (`requestId`, `answer: {decision}`, plus `alwaysAllow` or the owner's `message` when the answer had them) ends it, **written before Claude Code hears the answer**, so the log reads in the order things happened. `decision` is `allow` or `deny` (the owner's), `cancelled` (Claude Code withdrew the ask: its abort signal fired) or `interrupted` (the runtime stopped, or found at its next start that the previous one had, with the ask open; nobody could ever answer it). Every ask gets exactly one.
- **Open means asked and not answered**, and `openPermissionAsks(entries)` in `agent-protocol.ts` is the one definition, used by the runtime (to close the asks a dead runtime left, at its start, and at `finish()`) and by the browser (to show them). A device that connects, reloads or reconnects therefore sees an open ask from its replay, with no extra message. A `sync` that does not carry the whole log (`tailTurns`, [below](#long-conversations)) still includes every open ask: `AgentLog.readTail` puts the ones from before its start first.
- **Every device is equal; the first answer wins.** `answer {requestId, decision}` goes to the runtime, which looks the ask up. If it is not open, the answer is ignored and nothing is said, not even an `error`: answering on two devices at once is normal. Otherwise the ask is taken out, `permission_answered` is logged and broadcast, and the SDK's promise is resolved. **The card goes only when that entry arrives**, never by a local decision, so the device that answered second loses its card exactly as every other does.
- **The runtime builds the SDK's result.** Allow is `{behavior: "allow", updatedInput: <the ask's own input>, toolUseID}` and Deny is `{behavior: "deny", message, toolUseID}` whose message tells Claude the owner declined, to stop and wait (it comes back as the tool's error). A client says only which choice: it can never supply `updatedInput` or `updatedPermissions`. The choices are `PermissionReply` in `agent-protocol.ts`: `allow`, `allow` with `alwaysAllow: true` ("Yes, don't ask again": the runtime echoes the `suggestions` it stored as `updatedPermissions`, and only if Claude Code offered some and did not set `suppressAlwaysAllowRule`; otherwise it is a plain allow, and the logged answer says so), `deny`, and `deny` with a `message` ("No, and tell Claude what to do differently": the result's message is Claude Code's own rejection sentence followed by `To tell you how to proceed, the user said:` and the owner's words, which Claude reads as the tool's error). `allow` with `answers` ({question text: answer}) is the answer to an AskUserQuestion ask and `deny` with a `message` is plan feedback, the same way ([Questions and plans](#questions-and-plans)). `AskUserQuestion` and `ExitPlanMode` arrive as ordinary asks and are told apart by `toolName`.
- **No connection, no answer.** `AgentConnection.send` returns false and drops the message while reconnecting (it is never queued): for an answer that means the panel's choices are disabled, as Send is, and "Reconnecting…" says why. A late Allow, sent after the owner lost the connection and forgot the question, would be worse than a dropped one; after the reconnect the replay shows whether another device answered meanwhile. After a click the buttons stay off until the entry arrives, so a double tap cannot answer twice, and come back if the connection drops first (the answer may not have arrived).
- **Several asks can be open** (a subagent asks while another is). The Pane shows the oldest and says how many wait behind it.
- **A Stopped Agent has no open asks.** `useAgentConversation` returns none once the Session `ended` or the server has said `stopped`, whatever the log says: the runtime closes them as `interrupted` when it exits by itself and at its next start if it was killed, but a runtime killed outright leaves its last ask open in the log, so the Stopped Transcript marks it (`buildItems` with `stopped`) as "Not answered, the Agent stopped" on its tool call, as it does an ask logged `interrupted`.

### Questions and plans

AskUserQuestion and plan approval (#147) are two more kinds of ask, with the same life as a permission ask (logged, replayed to every device, first answer wins, gone when the `permission_answered` entry arrives). What differs is the panel and what the runtime accepts.

- **AskUserQuestion** (`input.questions`: one to four of `{question, header, options: [{label, description}], multiSelect}`, read by `askedQuestions` in `src/shared/agent-questions.ts`, which the runtime and the browser share). The answer is `allow` with `answers`: each question's text to the label chosen (a multi-select's labels joined by `, `) or the owner's own words (the panel always offers `Other`, as the terminal does). The runtime accepts it only if it answers **exactly** the questions it holds (`answersFit`); anything else, and a bare `allow`, is ignored like any answer to an ask that is not open, and the ask stays. It then sends Claude Code `{behavior: allow, updatedInput: {...input, answers}}`: the client never supplies `updatedInput`. A `deny` (`Skip the questions`) is the usual denial. An ask whose input is not in this shape (a newer Claude Code) is a permission ask like any other.
- **Plan approval** is `ExitPlanMode`, whose `input.plan` is the plan's markdown (Claude Code has already written it into its own plans folder, as the terminal does; k-bench saves nothing). Approve is a plain `allow`; reject is `deny`, with the owner's feedback as `message` when there is some. Claude carries on in the same turn either way.
- **The mode after approval.** Approving leaves plan mode. Whether the real Claude Code reports it in a `system/status` is **unconfirmed**, so `PermissionModeTracker` (`mode.ts`) remembers the mode before plan mode and the tool call of each approved plan; when that call's result arrives and the runtime still thinks it is in plan mode, it asks Claude Code for that mode (`default` when it started in plan mode) and publishes it. If Claude Code reported the change first, nothing is done. The terminal's other plan choices (auto-accept edits, clear the context first) are not offered: the owner switches mode with the mode line.
- **The Transcript** gets a line from the answered entry, the same `permission` item with a `topic`: `⎿ question: Which database? → SQLite` (a line per question; `skipped` for a denial) and `⎿ plan: approved` / `rejected` / `rejected: <feedback>`.

### Permission mode

The mode line under the input shows Claude Code's permission mode, and a tap or Shift+Tab switches it (#139). Claude Code owns the mode: the owner's settings start it, plan approval leaves plan mode, a command can change it. So the runtime (`src/agent-runtime/mode.ts`, `PermissionModeTracker`) never assumes it; it takes it from what Claude Code says and publishes it as `status.mode`, to every connection and to every one that connects later, so every device shows the same.

- **Where it comes from:** the `initialize` reply's `current_permission_mode` (so it is known before any turn, and before the runtime listens), each turn's `system/init.permissionMode`, any `system/status.permissionMode` (how Claude Code reports a change it makes itself), and a switch Claude Code accepted. A mode change appears only in `status`, not in the log: it is a state, not part of the conversation.
- **Switching:** `set_permission_mode {mode}` calls the SDK's `setPermissionMode`. The client sends the **target** (the next mode after the one it shows, `nextPermissionMode`), not "next", so two devices tapping at once ask for the same mode and it is set once. The line changes only when the runtime's `status` arrives, never by a local guess. If Claude Code refuses, nothing changes and nothing is said.
- **The cycle** is `PERMISSION_MODE_CYCLE` in `agent-protocol.ts`, in the order the real TUI's footer cycles (read by the live check, #161): Ask before edits (`default`, which the TUI labels `manual mode on`), Accept edits, Plan mode, **Auto mode**, and back. **`auto` is offered only where the model supports it**: the runtime reads `models[].supportsAutoMode` from Claude Code's first reply (`autoModeSupported` in `mode.ts`, finding the model by the latest `init`'s model, or by the launch alias before any turn; an unknown model says no) and tells every client in `status.autoMode` (additive; `AGENT_PROTOCOL_VERSION` stays 1). Whoever cycles uses `nextPermissionMode(mode, autoMode)`. If Claude Code refuses `auto` (the owner's settings can), nothing changes, and the runtime stops offering it (`status.autoMode` goes absent) until the model changes, so that the next tap moves on instead of asking for `auto` again. The runtime accepts nothing from a client outside the cycle, so no client can switch on `bypassPermissions` (it needs an opt-in made outside k-bench). A mode outside the offered cycle (the owner started in `bypassPermissions`, or in `auto` on a model without it) is shown, and the next switch goes to `default`.
- **The browser:** `ModeLine` (a button named `Permission mode`) under `Composer`, which takes Shift+Tab on desktop (`onShiftTab`, with `preventDefault` so the focus stays in the box). Both call `cycleMode()` from `useAgentConversation`. Disabled while reconnecting or ended, as Send is.

## The `/` menu and typed commands

Ticket #150: Claude Code's commands and skills from the input box, with no panels.

- **Typed commands are ordinary prompts.** `/context`, `/compact`, `/model opus` go to Claude Code as the text typed, never marked as composed by the client (the same `prompt` message as any other), so Claude Code runs them as it does in a terminal. What a command prints arrives, as the live check recorded from a real Claude Code (#161), as an **assistant message of model `<synthetic>`** holding the output as text, with the same text wrapped in `<local-command-stdout>` as the message's `local_command_source` (also `local_command_run: {command, args}` for `/model`, `local_command_outcome: {kind: "unavailable_headless"}` for a command that isn't available), followed by a `user` echo (`isReplay`, the prompt's own `uuid`) of the command as markup, `<command-name>/model</command-name> <command-message>.. <command-args>haiku</command-args>`. `buildItems` shows the reply as a `command_output` item (it keeps reading `system/local_command_output` too, and a user `<local-command-stdout>`, which is how a terminal's saved conversation holds it), and reads the markup echo as the command line `/model haiku` when it is not k-bench's own prompt (a turn imported from the terminal); k-bench's own echo has its prompt's `uuid` and is not shown again. `/compact` printed no output at all: `⎿` and the reply, muted, folded after eight lines (`CommandOutput`, accessible name "Command output"). A command that opens a panel in the terminal answers however Claude Code answers there ("isn't available in this environment"): that reply is an [Unsupported row](#unsupported-rows) (#153) and **not** also a `command_output` line (`buildItems` leaves it to the row).
- **The header follows `/model`** because it reads the model of the latest `system/init`, and a command is a turn like any other. Confirmed by the live check (#161): a typed `/model haiku` is followed by a `system/init` naming the model, in the same turn, before the command's reply.
- **The list** is `CommandList` (`src/agent-runtime/commands.ts`): the SDK's `supportedCommands()` at start (which keeps the latest list), replaced whole by every `commands_changed`, with rows sharing a name collapsed to the one Claude Code owns (`builtin`). The runtime hands it to `ClientHub.setCommands`, which sends the `commands` message to each connection after its `replay`, and to every synced one when it changes. It is not in `status`: it is large, and the server's status connection has no use for it.
- **Terminal-only entries** are named only by `terminal_slash_commands` in a turn's `system/init` (the SDK says phone and remote interfaces should hide them), **not** in the reply to the SDK's first request. So: before the Agent has had a turn, **every** command is offered, including ones that make no sense on the web (`/exit`), because k-bench keeps no list of its own and guessing which are terminal-only would hide commands that work. The first `init` removes them from the menu on every device. The runtime remembers the last `init`'s list and, when it starts again (Restart, a new runtime after an update), starts from the one in the log, so an Agent that has had a turn never offers them again. Choosing one of those before the first turn does what Claude Code does with it: a reply, or "isn't available" (#153).
- **The menu** (browser): `commandQuery(text)` in `web/src/agent/slashCommands.ts` opens it only while the whole input is `/` and the start of a name (`/`, `/co`); once a space follows the name it is closed, so `/model opus` is plain text, and so is a prompt that merely contains a slash. `matchCommands` lists names that start with what was typed, then aliases that do, then names that contain it, each alphabetically. `useCommandMenu` (`components/agent/`) holds the open state and the keys, `Composer` owns the text and writes the pick, and `PickerMenu` draws it: a `listbox` named "Commands" of `option`s (name, argument hint, description) above the input, with the focus staying in the input (`aria-activedescendant`).
- **Keys.** While the menu is open it owns Up and Down (they move the active row: they never recall prompt history, and a recalled prompt that happens to be a command does not open the menu), Tab and Enter (insert the name and a space, nothing more: `completion`), and Escape (closes the menu until the text changes; it does not interrupt). A name or alias already typed in full is complete, so Enter then sends it. A tap on a row picks it, which is how a phone does it. Shift+Tab still cycles the permission mode.
- **Reuse for `@` (#160).** `PickerMenu` and its `PickerOption` (`label`, `hint`, `detail`) know nothing of commands; `useCommandMenu` is the pattern for a second hook (query from the text, matches, active row, `handleKey`, a pick the input writes). `Composer` takes one more prop, `commands`, and renders the menu in one place. The keys are shared: `handlePickerKey` (`pickerKeys.ts`) is what both hooks' `handleKey` call.

## The `@` file picker

Ticket #160. **Follows a default not yet confirmed with the owner**: the SDK exposes no file picker, so this is k-bench's own, over the Workspace folder. Typed `@path` mentions are untouched and still pass through as typed (the `prompt` is the text as it stands; Claude Code expands them).

- **When it opens** (`fileMention(text, caret)` in `web/src/agent/fileMentions.ts`): while the caret is in a word that starts with `@`, the `@` at the start of the text or after whitespace, so `you@example.com` never opens it and a space after the word closes it. It follows the caret, so an `@` in the middle of a prompt works. `useFileMenu` (`components/agent/`) is the second hook beside `useCommandMenu`; `Composer` tracks the caret (`onSelect`) and shows whichever is open in the one `PickerMenu` (a `listbox` named "Files", the file's name with its folder dimmed after it). The two never open together: `/` needs the whole text to be the command.
- **Asking** (`GET /api/sessions/:id/files?q=`, `Service.searchAgentFiles`, `src/server/file-search.ts`): after a 100 ms pause in typing, the hook asks for what follows the `@`. It opens only when the answer is for what is typed now and is not empty, so an answer to an earlier word is never picked from. Only a Claude Agent answers (404 otherwise).
- **Which files.** In a git repository (a folder inside one counts): `git ls-files --cached --others --exclude-standard`, so tracked and untracked files, and **not** git-ignored ones; the Host's own git, with `GIT_DIR` and its kin removed from the environment so the owner's shell cannot point it elsewhere. Anything else: a walk of the folder that skips `.git` and `node_modules` and stops at 50,000 files. A file matches when its path contains the query, in any case; best first: its name starts with the query, its name contains it, its path does; then shallower, shorter, alphabetical. At most 30 (`MAX_FILE_MATCHES`). Nothing typed lists the shallowest files.
- **Staying inside the folder.** The query is only matched against names found under the folder; it is never joined to a path, so `../x` or an absolute path match nothing. Every result is also checked with `realpath` to be a regular file inside the folder's real path, which drops files git still lists after they were deleted and symbolic links (to a file or a folder) that lead out; the walk never follows links at all.
- **Picking** (a tap, Tab or Enter) replaces the whole word with `@relative/path` and a space, which also closes the picker, and puts the caret after it. Text goes through `edit()`, so the draft saves. The picker owns Up, Down, Tab, Enter and Escape while it is open, as the `/` menu does: the arrows do not recall history and Escape closes it without interrupting. Escape closes it only until the text changes.
- **Not verified**: a path with a space in it is inserted as it is (`@my file.ts`), and whether Claude Code reads that as one mention is not confirmed; the live check (#161) should record it. A Workspace that is not a git repository has no `.gitignore` to read, so only `.git` and `node_modules` are left out.

## Subagents and background tasks

Ticket #149. Claude Code runs subagents (the `Agent` tool) and background work (a `Bash` command with `run_in_background`, monitors, workflows) as **tasks**, which can outlive the turn that started them. They reach k-bench in two places.

- **The status** (`src/agent-runtime/tasks.ts`, `TaskTracker`). The runtime keeps the tasks running now and publishes them as `status.tasks`, absent when none; the server passes them on as `SessionState.agent.tasks`. **#155 (Open in terminal) reads that list for "what would stop".** `task_started` adds a task, `task_notification` (or a `task_updated` whose status is final) removes it, and `background_tasks_changed` is the full list of the background ones and **replaces** what was held, so a missed bookend cannot leave one running for ever. A task that blocks its tool call (a foreground subagent) cannot outlive its turn, so the turn's `result` removes it. `ambient` and `skip_transcript` tasks are not activity and are left out, as the SDK says hosts should. `stop_task {taskId}` goes to the SDK's `query.stopTask`, which stops that task alone; Claude Code answers with a `task_notification` of status `stopped`. The runtime forwards the id unchecked: Claude Code refuses one that is not running, and that is not an error.
- **Activity ignores them.** A subagent's own frames (`parent_tool_use_id`) and a task's `tool_progress` (`task_id`) can arrive after the turn's `result`, and no `result` would end a turn they started, so `Activity` does not take them for one: an Agent with only tasks running is Idle.
- **The Transcript** (`web/src/agent/tasks.ts`, `TaskBuilder`, fed by `buildItems`) reads the same messages from the log. A subagent is an `Agent` tool call plus a task with the same `tool_use_id`, and a background command is a `Bash` call that returns at once plus one, so the task is put **on the tool's own line** (`ToolItem.task`), not on a second one: the line's mark stays a spinner while the task runs even if the tool call returned (`toolMarkWithTask`), and goes green when it is done, red when it failed or was stopped. A task whose tool call is not among the items is a line of its own (`TaskItem`, `kind: "task"`, `Subagent(description)` or `Background task(description)`). Under the line (`TaskDetail`): the latest `task_progress` (`3 tool uses · 1.2k tokens · 12s · Grep`) and, while it runs, its **Stop** button (accessible name `Stop <description>`; the bare name `Stop` is the Agent's own). The button sends `stop_task` through `StopTaskProvider`, which `AgentPane` provides, and is disabled while reconnecting. A task still running when its turn's `result` comes (and it did not outlive turns) or when a runtime starts or stops is shown interrupted (red). `seq` is the `task_started` entry's for a line of its own.
- **Progress** is what `task_progress` carries (tool uses, tokens, duration, the last tool, and `summary` when present). The SDK can also ask Claude Code for a model-written summary of each subagent (`agentProgressSummaries`); it is **not** turned on, because it forks the subagent's conversation about every 30 seconds on the owner's subscription. It would be one option in `session.ts`.
- **What the live check recorded (#161):** an `Agent` tool call launched its subagent **asynchronously** (the tool result carries `tool_use_result: {isAsync: true, status: "async_launched"}`), so it was **backgrounded** at once: `background_tasks_changed` listed it (before its `task_started`, which says `is_backgrounded: true`), and it ended with `task_updated` (`status: completed`), `task_notification` and `background_tasks_changed` with an empty list, here before the turn's `result`. A finished task can start a turn nobody sent (Claude is told), with its own `command_lifecycle` of none. `TaskTracker` and the browser's `TaskBuilder` read all of that correctly: a backgrounded task stays until Claude Code says it ended. **Still not seen on a real Claude Code:** a subagent that blocks its turn (`is_backgrounded: false`), a background task that is still running at a turn's `result`, `stopTask` on a real task, and what an interrupt does to one; the fake's foreground and `stop_task` shapes follow the SDK's types.

## State: Idle, Working, Waiting for you

What an Agent is doing is one word in `status.state`, which the runtime decides (`src/agent-runtime/activity.ts`, `Activity`) and pushes to every connection whenever it changes:

- **Waiting** is `PermissionAsks.count > 0`: an ask is open. It wins over Working.
- **Working** is a turn running, **whoever started it**. A prompt k-bench sent counts from the moment it is sent, until its `result`, so there is no Idle gap between a turn and the prompt queued behind it. A turn nobody sent (`/loop`) is seen from Claude Code's messages: the first `system/init`, `stream_event`, `assistant`, `user` or `tool_progress` after Idle starts it, and the `result` ends it. A late `system` message after a `result` (a hook, a background task) does not start one.
- **Idle** is neither.
- `turnStartedAt` (the runtime's clock, which is the Host's) is set when the Agent leaves Idle and kept through Working and Waiting, so "Working · 42s" is the turn's time, not the wait's. It is absent when Idle.
- `bell` is not a state but rides on the same `status`: the Agent's Bell, held by the runtime (`AgentBell`) and cleared by a `view {visible: true}` from any connection. How it works is in [Bell](bell.md#a-claude-agents-bell). `AgentStatuses.bellOf` hands it to `Service.getState`, which uses it as `SessionState.bell` for an Agent in place of tmux's.

Claude Code is also asked to report it itself (`CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1` in the environment the SDK gives `claude`, the owner's own plus that one): `system/session_state_changed` (`running`, `requires_action`, `idle`). When it comes it is believed (`idle` ends the turn and clears every counted prompt). **It is not relied on**: whether the real Claude Code sends it for a turn nobody sent has not been confirmed, so the message-based rule above carries the state alone (the fake can be told never to send it with `configure({ sessionStateMessages: false })`, and `test/claude-agent-state.test.ts` covers a turn nobody sent both ways). A command that takes no turn must not leave a prompt counted for ever: `conversation_reset` and Claude Code's `idle` clear the count as well as `result` lowers it.

The server (`src/server/agent-status.ts`, `AgentStatuses`) keeps **one status connection per running runtime**, opened with `AgentRuntimes.connect`. It never sends `sync`, so it receives only `hello` and `status`, and it keeps the last of each in memory: a cache of what the runtime said, dropped when the connection drops or the Agent stops running, never stored. `Service.getState()` is what starts and ends the watching: each read already asks tmux which Sessions live, and tells `AgentStatuses.follow` which of the Claude Agents among them run, so a new Agent, a restarted one and every Agent after a k-bench restart are picked up the same way. At startup `startServer` waits (up to three seconds) for what each running Agent says before the first state is read (`Service.watchAgents`), so a client never sees an Agent that was Working shown as anything else. Every change calls `feed.notify()`, so it reaches the events socket at once. The state is `SessionState.agent` (`src/shared/state-protocol.ts`: `state`, `turnStartedAt`, and the `claudeVersion` and `runtimeBuildId` from the hello); an Agent with no status heard yet has no `agent` and is shown like any running Session. Stopped is not a runtime state: it is the Session's `status`.

The browser (`web/src/agentState.ts`) turns that into the four things shown: the dot and row edge in `SessionRow` (green dot and faint edge for Idle; spinning green ring and green edge for Working; pulsing orange for Waiting for you, with `row-waiting` beside `row-pulse` so that orange wins on a row that has both; hollow and no edge for Stopped), a collapsed `WorkspaceRow` that turns orange while any Agent in it waits, and the top bar's `● Idle`, `◌ Working · 42s`, `● Waiting for you`, `○ Stopped` in `PaneLabels`. The seconds count from `turnStartedAt` on the browser's clock, so a device whose clock is wrong shows them wrong. The dot's accessible name is `<name> idle`, `working`, `waiting for you` or `stopped`; a Waiting row also carries a `role=status` text `<name> is waiting for you` (and a collapsed Workspace `<name> has an agent waiting for you`), which is what tests look for, as the pulse is animation.

## Stop, Restart and the Stopped Transcript

- **Stop** is `POST /api/sessions/:id/stop` (`Service.stopSession`, Agents only), from the row menu. When the row's state says the Agent is working or waiting, the browser asks "Claude is working. Stop anyway?" first (`StopAgentDialog`). The server sends `shutdown` ([the runtime's end](#the-agent-runtime-src-agent-runtime)): the runtime closes open asks as `interrupted`, interrupts a running turn, finishes the log and exits; `AgentRuntimes.shutdown` kills the tmux session if it has not exited after four seconds. The Session then reports `stopped`, which is just "no tmux session" (ADR-0002).
- **Why it stopped** is in `exit.json`, which the launcher deletes at every start: the runtime's own words for every exit it controls (`You stopped it`, Claude Code's error, `The Agent Runtime failed: ...`, a signal); `The Agent Runtime exited unexpectedly` when only the launcher saw it end (killed outright); and, when there is no record at all, that the Mac went down with it. `AgentRuntimes.stoppedReason` picks the words.
- **Crashes are never restarted.** Nothing but the owner's Restart starts a runtime for an existing Session: not a crash of the runtime or its Claude Code, not a restart of k-bench, not the Host going down.
- **The Stopped Transcript.** On the agent WebSocket of an Agent that is not running, `AgentSockets` answers `sync` and `page` from the log on disk with `answerSync`/`answerPage` (the runtime's own code, over an `AgentLogReader`, which never writes) and ends the `sync` with `stopped {reason}`. It ignores every other message. The Pane (`AgentPane`, shown for a Stopped Agent too, `key`ed by the Session's status so Stop and Restart each open the right kind of connection) shows the Transcript with the Raw switch, scroll-back and all, and `StoppedBar` where the input was: `⏹ Stopped: <reason>` and **Restart**. `stopped` also marks the log final for `buildItems`: a tool call still running becomes interrupted, and a tool whose ask is open or was closed as `interrupted` shows `⎿ Not answered, the Agent stopped`, so it never reads as approved. A killed runtime writes none of that itself.
- **Restart** (`restartSession`, the same call from the row menu and the Stopped Pane): a new runtime on the same log, `mode: "resume"` with the stored conversation ID and Launch options (or `start` if no prompt was ever sent in it: `--resume` fails for a conversation Claude Code never saved). The runtime closes any ask a killed predecessor left open at its start.
- **`/clear` moves the conversation (#151).** The log stays one continuous file, but the Claude conversation changes: `conversation_reset` is followed by a `system/init` whose `session_id` is the new conversation (the reset's own `new_conversation_id` is **not** it, the live check #121), which Claude Code sends with the next turn, so a prompt can come between the two; until then the Agent is in the old one. `ConversationTracker` / `conversationOf(initial, entries)` in `src/agent/conversation.ts` reads that from the log: `id` (where a resume goes) and `saved` (whether a prompt was sent in it). The runtime builds one at its start, so a Restart resumes the conversation the owner was last in even if nothing else noticed the change (the store's ID is only the starting point), and starts a fresh one under the new ID when nothing was sent in it yet. It also feeds every entry it logs to the tracker and puts `conversationId` in its `status`; `AgentStatuses.onConversation` hands that to the `Service`, which `Store.setConversationId`s it, so the stored ID is the new one for as long as the Agent's status is being followed (it is followed while the state is read, as for every status field). Whatever resumes an Agent's conversation other than the runtime (Open in terminal, #155) should take the stored ID, or `conversationOf` over the log for one that is not running. The Transcript shows `conversation_reset` as a `divider` (below).
- **The folder reconciler**: `startServer` deletes every `agents/<id>` with no Session row, once, after killing orphan tmux sessions.

## Open in terminal

Ticket #155. `POST /api/sessions/:id/open-in-terminal` (`Service.openInTerminal`) switches **the same Session** from Claude Agent to Claude TUI; the web's conversation stays Claude's one conversation (ADR-0008).

- **The server** shuts the runtime down as Stop does (`AgentRuntimes.shutdown`: clean, killed after four seconds; a Stopped Agent has none), **then** reads the Session again, sets `sessions.interface` to `tui` and calls `startStopped`, the code that restarts a Claude TUI: `claude --resume <conversation ID>` with every stored Launch option, falling back to `--session-id` only when the conversation was never saved. **Two orderings are load-bearing.** The conversation ID is worked out after the shutdown, because `/clear` (#151) changes it until the runtime has ended, and the stored ID is only fresh while the server follows the Agent's status: `conversationOf(stored, log)` over the now-final log says which conversation the Agent is in, and a different answer is stored (`setConversationId`) before Claude Code starts. The interface flips only once the runtime's tmux session is gone: while it is `tui` and that session still exists, `hasRunningShell` would let a terminal attach to the hidden runtime (ADR-0007). If the terminal cannot start, the interface goes back to `agent` and the Session is a Stopped Agent. The same in-flight map as Restart means a double tap, or another device's Restart, shares one transition.
- **What stays.** The Agent's folder (log, images) stays after the switch; it is what Open in web (#156) resumes from. Deleting the Session removes it for any Claude Session, not only a current Agent. The store's `interface` is "the interface last used", so Restart after a Host restart resumes in it with no further code: `startStopped` already branches on it.
- **Every device follows** because the snapshot's `interface` changes: `Pane` renders `TerminalView` (so Extra keys and Smart typing come with it), and the agent WebSocket of a device still showing the Agent closes with 4410. Per-device drafts are in the browser's storage and are kept.
- **The confirm is the browser's** (`web/src/useOpenInTerminal.tsx`, `agent/whatWouldStop.ts`, `OpenInTerminalDialog`), from the state it already has: Working, Waiting for you, and each of `agent.tasks` (listed). Idle with nothing running, Stopped, and an Agent not yet heard from go straight through. The one hook serves the row menu (`SessionRow`), the top bar (`PaneLabels`, a button beside the label's note, an icon on a phone) and Unsupported rows (a context from `AgentPane`).
- **Rewind.** Nothing to build: file checkpointing is on from the first launch, so the terminal's `/rewind` can restore code the Agent edited (to be confirmed by the live check, #161).

## Updating under a running Agent

Updating k-bench is safe at any time, and moving an Agent to the new k-bench's runtime is the owner's call (ADR-0007, ADR-0008). An update replaces the app folder and restarts the server; a running Agent Runtime is a process of its own, running from its own copy in `<dataDir>/runtimes/<build id>/`, so it is not touched (see [Packaging](packaging.md#the-agent-runtime)).

- **Which build an Agent runs** is in its hello (`runtimeBuildId`, the SHA-256 of the runtime file, which the runtime computes from its own file). The server's status connection keeps it (`AgentStatuses`), and `SessionState.agent.runtimeBuildId` carries it.
- **Update available** is `SessionState.agent.updateAvailable`, set by `AgentStatuses.stateOf` only when that build ID differs from `AgentRuntimes.current.buildId`, the build this server installed at startup. A k-bench release whose runtime code is unchanged has the same build ID, so a running Agent shows nothing and is not touched; the runtime is bundled from `src/agent-runtime`, `src/agent`, `src/shared` and the SDK, so any change to those, or an SDK bump, is a new build. The Pane shows `UpdateBar` above the input: "Update available", and **Restart**, which asks "Claude is working. Restart anyway?" while a turn runs (a restart interrupts it). Until then the Agent keeps working as it was. A server that downgrades also sees a difference; the word "update" is then loose, and the restart still lands on the installed build.
- **Restart** is `POST /api/sessions/:id/agent/restart` (`Service.restartAgent`; the Stopped Pane's Restart stays `POST .../restart`, which leaves a running Session alone): `AgentRuntimes.shutdown` (the runtime closes open asks as `interrupted`, interrupts the turn and exits; killed after four seconds if it does not), then the same start as a Stopped Agent's Restart, `mode: "resume"` with the stored conversation and Launch options, on `current`. The Agent counts as running to the agent WebSocket for the whole of it (`Service.replacing`), so Panes that were open wait for the new runtime and reconnect to it instead of being told the Session ended (4410); they get its hello with the new build ID and the `updateAvailable` flag goes away. Two requests at once share one restart.
- **Deleting old builds.** `Service.getState` (which runs on every state read and push, and once after the startup wait in `watchAgents`) asks `AgentStatuses.buildsInUse` for the build each running Agent's last hello names, and calls `AgentRuntimes.pruneRuntimes` with them. If any running Agent has not said hello yet the answer is "unknown" and nothing is deleted. A folder goes after the last Agent on it is Stopped, restarted or deleted; the current build's folder never does. (A runtime has already read its file when it starts, so this is about not deleting what may still be needed, not about a running process.)
- **Protocol mismatch.** `AGENT_PROTOCOL_VERSION` (`src/shared/agent-protocol.ts`) is the protocol's number; it only grows by additions within one number and is bumped only for a change that cannot be made that way. Every connection opens with a hello that names the runtime's number, and that first message is part of the contract for every number. When it is not the number this k-bench speaks: the browser's connection (`agentConnection.ts`) passes on the hello only and nothing else, and sends nothing, and does not move its `lastSeq`; `useAgentConversation` reports `incompatible`, and the Pane shows `UpdateBar` with "can't be read by this one" and **Restart** in place of the conversation and the input. The server does not read what such a runtime says either: `AgentStatuses.stateOf` reports no `agent` state and no Bell for it, so its row shows as any running Session. Restart is the same `agent/restart`; the new runtime's log continues the old one and the conversation resumes. The shutdown message of an unknown protocol may not be understood, in which case the restart waits the four seconds and kills it.
- **Tests.** `test/claude-agent-update.test.ts` (same runtime: untouched, no update; changed runtime: update shown on each Agent, they keep working, Restart moves one and carries on its conversation, the old build is kept while another Agent runs it and deleted after; a runtime on another protocol number: Restart resumes the conversation) and `e2e/claude-agent-update.spec.ts` (the Pane's update strip and the mismatch strip, each with Restart). The second runtime is `instance.runtimeVariant(label, {protocol?})`, started with `instance.start({ agentRuntimeFile })` ([Test seams](test-seams.md#claude-agents)).

## Open in web

Ticket #156. `POST /api/sessions/:id/open-in-web` (`Service.openInWeb`) is Open in terminal run backwards, for a Claude TUI running or Stopped: it stops the terminal's tmux session, **then** sets `interface` to `agent` (so nothing can attach a terminal to the runtime's hidden session), then `startStopped` starts the runtime in `resume` mode with the stored Launch options and `--import-terminal`, and the server waits for it as for any Restart. Before the terminal goes it checks what would stop the Agent starting (the folder, the installed runtime), and if the start fails anyway the interface goes back to `tui` and the Session is a Stopped Claude TUI. The `replacing` set makes the Session count as an Agent while this runs, so Panes that already show the Agent wait for the runtime instead of being closed with 4410. Every device follows because the state snapshot's `interface` changes: `Pane` renders the conversation.

**The import** is the runtime's, at its start, before Claude Code starts and before its `runtime started` entry (`importTerminalTurns` in `main.ts`; the rules are the pure `planTerminalImport` in `src/agent-runtime/terminal-import.ts`). It reads the conversation once with the SDK's `getSessionMessages` (`includeSystemMessages`) and appends `divider` entries and `sdk` entries (the SDK's `type`, `uuid`, `session_id`, `message`, `parent_tool_use_id`; a user message someone typed gets `isReplay: true`, so the Transcript shows it as a prompt as it shows the echo of one k-bench sent). The log then reads: the Agent's turns, the Agent stopping, `In the terminal`, the terminal's turns, `Back in web`, the new runtime starting.

- **Where it left off.** The IDs k-bench holds: each `prompt` entry's `id` (Claude Code keeps the client-set ID as the message's `uuid`) and the `uuid` of every `sdk` entry already in the log. The last message of the conversation that is one of them is the anchor. After one of k-bench's own prompts, that prompt's own reply is in the log already, so the import skips to the next thing someone typed; after any other known message it starts right after it. Messages already in the log are never added twice, which also makes a second round trip with nothing new in the terminal import nothing.
- **Compacted.** What the live check found in a real terminal's saved chain after `/compact` (#161, kinds only): it **starts with a system message** (the boundary), then the summary (a user message with `isCompactSummary` and `is_meta`), then the conversation (the web's prompts **are still in it**, so the import takes the _found_ path, not the one below), then the command's own output (user messages with `isCompletedLocalCommand`). So the import says the terminal compacted **whichever way it was anchored**: whenever the chain holds a compaction summary the log has not seen (the first divider reads "Compacted in the terminal: earlier turns above are from before"); a summary that lies before the anchor is imported first rather than lost; and an imported message keeps what marks it as Claude Code's own (`isCompactSummary`, `is_meta`, `isCompletedLocalCommand`; `asEntry` used to drop them) and is never made a replayed prompt (`startsATurn`). The Transcript shows the summary as an output line, a local command's output as a `command_output` line, and other `is_meta` messages not at all. When none of the web's messages is in the chain, a chain that begins with a system message is still told as compacted and starts from the summary (the older heuristic, kept for a chain that was rewritten).
- **No anchor at all.** The log holds no message, as for a Session that began as a Claude TUI: the whole conversation is imported. This default is not in the spec. When the log has messages and none is in the conversation (and it is not compacted), nothing is imported: a duplicate conversation would be worse than a gap.
- **Nothing new** adds neither divider. A `/clear` in the terminal is not followed back: the runtime resumes the conversation the Agent had.
- **Resuming.** A runtime resumes only a conversation it knows was saved, which the log said by a `prompt`; a `divider` says it too (`ConversationTracker`), because a Session that began as a Claude TUI has no prompt in its log. A conversation the terminal never saved is started, as for any Restart. If the read fails, the runtime still starts and says so in a divider.
- **Tests' Claude Code folder.** The SDK reads `CLAUDE_CONFIG_DIR`, but the tmux server's environment is not the owner's or the test's, so tests give the server `InstanceConfig.claudeConfigDir` and it passes `--claude-config-dir` to the runtime, which sets the variable first thing. Nothing sets it in production, where the owner's own environment reaches the runtime through the login shell. See [test seams](test-seams.md).

## Long conversations

A page opens on the latest turns, not the whole log, and the owner scrolls up for the rest (#141).

- **A turn** (`turnStarts` in `src/agent/log.ts`) runs from a prompt that follows a `result` (or the log's start) to the next such prompt; for a turn nobody sent, Claude Code's `system/init` stands in for the prompt. Whatever Claude Code says after a `result` (the Session going idle, a command completing) belongs to the turn that ended, and a prompt sent while a reply streams belongs to the turn it was sent in. So a turn is never cut between a `tool_use` and its `tool_result`, a message that is mid-stream is always in the tail, and a page boundary is always a turn boundary. What a later ticket's reducer needs of a turn's start (the header's `system/init`, a prompt's echo) is in the tail with it.
- **Fresh load.** The browser's first `sync` is `{afterSeq: 0, tailTurns: 5}` (`agentConnection.ts`; it is `afterSeq: lastSeq` with no `tailTurns` on every reconnect, so a connection never has a gap). The runtime answers with `AgentLog.readTail`: from the start of the fifth-last turn to the end, plus any open ask from before it, and `from` says where the range starts. `snapshot`, live entries and fragments are as before, because the message streaming now is always in the tail.
- **Scrolling up.** `page {beforeSeq, limit: 20}` with `beforeSeq` the `from` the browser holds, answered by `AgentLog.readPage` with the `limit` turns before it. The page's `from` becomes the next `beforeSeq`, so pages meet exactly, until `from` is 1. The reducer (`transcript.ts`) keeps `earliestSeq`, merges a page ahead of the entries held by `seq` (an ask already held is not added twice), and ignores a page that reaches no further back than what is held. `permissionAsks` and the snapshot's block count read `state.entries`, so they agree with a tail-only state.
- **The Pane** (`components/agent/useScrollBack.ts`) watches a sentinel at the top of the conversation with an `IntersectionObserver` (200px early), asks for a page when it shows and there is more, looks again after each page (a conversation still too short to scroll keeps loading until it is not), and moves the scroll position by the height a page adds above, in the same frame, so what the owner reads does not move. The scroller sets `overflow-anchor: none`: Safari has no scroll anchoring and two corrections must not both act. A request in flight is forgotten when the connection drops, and made again once it is back.
- **Old runtimes.** A runtime built before this ignores `tailTurns` and replies with no `from`, which the browser reads as 1: the whole log, nothing to page.

### Images

Showing Claude a screenshot (#159; this follows a default not yet confirmed with the owner). **Names go over the socket, bytes go over HTTP.**

- The browser checks an image against Claude's limits (`src/shared/agent-images.ts`: PNG, JPEG, GIF or WebP; **5 MiB measured on the base64 text**, as Claude measures it, so about 3.9 MB of file; 8000 pixels on the longest edge, which only the browser can count; 20 per message) and, if it passes, uploads it **at once** (`POST /api/sessions/:id/agent/images`, base64 inside JSON, so the `application/json` check stays a second line behind the Origin check; [API](api.md)). One that fails is never uploaded. Uploading at attach time keeps Send as quick with images as without; the cost is that an image attached and then removed stays on disk until the Session is deleted.
- The server checks type, size and the file's first bytes again, stores it as `<agent folder>/images/<uuid>.<ext>` (mode `0600`; `images/` is made without recursion, so an upload racing a delete fails instead of bringing the Agent's folder back) and answers its name.
- The `prompt` carries the names. The protocol accepts only `<uuid>.<ext>` names (`STORED_IMAGE_NAME`), so a client cannot make the runtime read another file. The runtime (`src/agent-runtime/images.ts`, `promptContent`) builds the SDK message's `content`: an image block `{type: "image", source: {type: "base64", media_type, data}}` per image, then a text block if there is text; with no images `content` stays the plain string. It does this **before** logging or counting the prompt, and a file that cannot be read becomes a short text note rather than an error, so a lost image never takes the Agent down. The log's `prompt` entry keeps the names, never the bytes.
- The conversation shows the images of a prompt above its text (`PromptImages`, from `GET .../agent/images/:name`). Deleting the Session removes the Agent folder, and the images with it.
- Browser: `web/src/agent/images.ts` (the checks), `useAttachments.ts` (state, upload) and `components/agent/Attachments.tsx` (thumbnails, the `Attach image` button, whose `accept="image/*"` input is the photo library on a phone). Accessible names: the button `Attach image`, the list `Attached images` of thumbnails `Attached: <file name>` each with a button `Remove <file name>`, the over-limit message a `role=alert`, and the sent images `Your attachment` in the list `Images sent`.

## The Agent folder: `src/agent/`

Node code shared by the server (which compiles it, `tsconfig.build.json`) and the runtime (which bundles it). It must never import from `src/server` or `src/agent-runtime`.

- `paths.ts`: every location, so the two sides cannot disagree. `<dataDir>/agents/<session id>/` holds `log.jsonl`, `agent.sock` (reached through a short link, [below](#the-sockets-path)), `exit.json` and `images/` (#159). `<dataDir>/runtimes/<build id>/agent-runtime.mjs` is an installed runtime. `agentsRoot`, `agentFolder`, `agentImagesFolder`, `agentLogFile`, `agentExitFile`, `runtimeFile`, `runtimeBuildId(bytes)` (SHA-256 hex), `makeOwnerOnlyFolder` and `ensureOwnerOnlyFolder`.
- **Permissions.** The parent and each Agent folder are mode `0700`, set with `chmod` after `mkdir` because the umask cuts `mkdir`'s own mode. There is no token: whoever can open the folder can reach the socket, and the socket file is `0600` too. **Only the server creates these folders.** The runtime and the launcher never `mkdir`, so a runtime still exiting cannot bring back a folder the server just deleted.
- `log.ts`: `AgentLogReader(file)`, which never writes (`readAfter(seq)`, `readTail(turns)` and `readPage(beforeSeq, turns)`), and `AgentLog(file)`, the runtime's, which adds `append(entry)` (numbers and stamps it, `appendFileSync`) and `last`, and `turnStarts(entries)` (what a turn is, [below](#long-conversations)). A write cut short by a crash is skipped on read. The runtime appends and the server reads it directly while an Agent is Stopped (#144), so both show the same history, and #144's Stopped Transcript opens with `readTail` and pages with `readPage` exactly as the runtime does.
- `replay.ts`: `answerSync(log, sync)` and `answerPage(log, page)`, the one definition of how a `sync` and a `page` are answered from a log. The runtime's hub uses them for a running Agent and the server for a Stopped one, so a Stopped Transcript is exactly what the Agent showed.
- `exit.ts`: `exit.json` (`{reason?, code?, signal?, at}`). tmux ends a Session's pane, and so the Session, the moment its command exits, so this file is the only place a reason survives. The runtime writes it with a reason in plain words on every exit it controls (Claude Code died, shut down, a signal, a crash); the launcher fills the gap when the runtime was killed (`code`, `signal`, no `reason`). Readers: `readExitRecord(folder)`. The launcher deletes it before each start.
- `lines.ts`: `LineSplitter`, the newline framing of the unix socket.

### The socket's path

A unix socket's path is limited: 103 characters on macOS (`sun_path` is 104 with its NUL), and on the newest macOS releases only the one-byte length of the address, about 253. `<dataDir>/agents/<id>/agent.sock` is 56 characters longer than the data folder, which the owner's login name or `K_BENCH_DATA_DIR` can make any length, and CI's temp folder alone made it 131: every Agent failed with `listen EINVAL`. Whether a given Mac accepts a long path depends on its macOS version, so never test a length on one Mac and conclude. The same code that works on one Mac fails on another.

So the socket is reached by a short path, `src/server/agent-socket-path.ts` (server only; the runtime is _given_ the path as `--socket-file`):

```text
/tmp/kb-<uid>/<16 hex of SHA-256 of the Agent folder's path>   ->   <dataDir>/agents/<id>
listen and connect on:  /tmp/kb-<uid>/<hash>/agent.sock         (about 40 characters)
```

- The link is a directory symlink and the socket path goes _through_ it: `bind` does not follow a link in the last component. The OS follows the link, but the length limit applies to the string given to `listen` and `connect`. The socket file is the real `agent.sock` in the Agent folder, so deleting the folder deletes the socket and nothing else is left but the link, which `removeFolder` removes.
- It is the same path for an Agent every time (the hash is of the folder's path, so a Dev, a test and the Installed instance never collide), so a k-bench that restarts reaches a runtime that kept running (ADR-0007) from the Session ID alone.
- `/tmp/kb-<uid>` is made `0700` and checked on every use (`lstat`: a folder, not a link, the owner's, no group or other bits). One that is not is refused with a plain message: another Mac user could pre-create it. It is not under `$TMPDIR`, which is long.
- The server makes the link (idempotently, by renaming a new one into place) before it launches the runtime, before every connect and before `shutdown`'s. macOS clears `/tmp` of files not used for three days; a link lost to that does not touch a running runtime, whose socket is in the Agent folder, and the next connect makes it again.
- At the server's start `removeStrayFolders` also removes every link whose folder is gone.

## The Agent Runtime: `src/agent-runtime/`

One long-lived Node process per Agent, started with `--agent-dir --socket-file --folder --claude --conversation --mode` (`args.ts`; arguments only, never environment, because the tmux server's environment is whatever its first command had). `main.ts` wires:

- `session.ts`, `ClaudeSession`: the Agent SDK's `query()` pointed at the owner's installed `claude` (`pathToClaudeCodeExecutable`, absolute) with everything the spec fixes: the `claude_code` system prompt preset, the default settings sources (`settingSources` left unset, so CLAUDE.md, skills, plugins, hooks, MCP servers and permission rules load as in the terminal), `includePartialMessages`, **`enableFileCheckpointing: true` from the first launch** (it cannot be added later, and `/rewind` in the terminal depends on it), `extraArgs: {"replay-user-messages": null}`, and the `canUseTool` the runtime hands it (`PermissionAsks`, [below](#permission-asks): it waits for as long as the runtime lives, there is no `defer`). `mode: "start"` is `sessionId` (`--session-id=`); `mode: "resume"` is `resume` (`--resume=`), except that when the log holds no prompt it starts instead, because Claude Code saves a conversation only after its first message.
- `asks.ts`, `PermissionAsks`: the permission asks Claude Code has made and nobody has answered: the `canUseTool` it hands the session, `answer()`, and the entries they write ([Permission asks](#permission-asks)).
- `hub.ts`, `ClientHub`: the unix socket (mode `0600` inside a `0700` folder), a hello for each connection, validation, `sync`, and the fan-out of entries and fragments. It knows nothing of Claude Code.
- `live.ts`, `LiveText`: the text so far of the message now streaming (by content block), fed by `main.ts` with every fragment and cleared on `message_stop` and on a `result`. It is what the hub sends as the `snapshot`. Subagent fragments are not kept, as the browser never shows them live.
- `main.ts`: logs every SDK message (`record()`: append, then send to every synced connection, so order is preserved), asks `getContextUsage()` at its start and after every turn for `status.context` (`ClaudeSession.contextUsage()`; a failure, from an older Claude Code or one going away, is caught and only leaves it out, never ending the Agent), and ends:
  - **Shutdown** (the `shutdown` command, or SIGTERM, SIGHUP, SIGINT): closes every open ask as `interrupted`, and for the `shutdown` command (Stop) interrupts a running turn and waits up to a second and a half for its `result`, so the log says it was interrupted; then records a `runtime stopped` entry (reason "You stopped it") and `exit.json`, closes Claude Code (`query.close()` kills it) and the socket, exits 0. The server kills the tmux session if the runtime has not exited a few seconds after `shutdown` (`AgentRuntimes.shutdown`).
  - **Claude Code ended or the runtime failed**: the same, with the reason, and exit status 1. Nothing restarts it. Claude Code and the runtime live and die together.
- It listens only once `claude` has said which version it is (`initializationResult()`), so every hello carries `claudeVersion`.
- **Subscription only** (`account.ts`, `subscriptionProblem`): right after that same reply, before it listens, the runtime reads `accountInfo()` (served from the first reply too). Anything but a first-party login with a subscription type, and no API-key source (`none`/`oauth`/absent are fine), ends it through the same path as above with a plain reason and exit status 1: `apiProvider` other than `firstParty`, an `apiKeySource` that is a key, or no `subscriptionType`. No prompt has been accepted by then, so no turn runs. Because the runtime has not said hello, `AgentRuntimes.waitUntilReady` turns the reason into the refusal: a **new** Agent is refused with 422 `Claude Agent could not start: <reason>` and nothing is left behind; a **restarted** one stays Stopped with the same 422, and its log ends with the `runtime stopped` entry carrying the reason. k-bench reads no credential and sets no environment variable.
- **The `claude` version**: not a runtime state. The hello carries `claudeVersion` and `sdkClaudeCodeVersion` (baked in at build time), and the browser compares them (`claudeVersionWarning` in `src/shared/claude-version.ts`, numeric `major.minor.patch`; a version it cannot read gives no warning) and shows the warning under the header (`AgentHeader`, note `Version warning`). It never refuses to start.

### The build and the build ID

`vite.runtime.config.ts` builds `src/agent-runtime/main.ts` into **one self-contained file**, `dist/runtime/agent-runtime.mjs`, with the Agent SDK inside (`build.ssr`, `ssr.noExternal`, one chunk), about 1.4 MB, run by plain `node`. `pnpm build:runtime` builds it and `pnpm build` includes it. The SDK is a development dependency only (pinned exactly; Dependabot gives it its own pull request), so the published package depends on no SDK, and installing k-bench never fetches the SDK's optional platform package with its bundled Claude Code (about 338 MB). The SDK's own version (`sdkVersion`) and the Claude Code version it was made for (`sdkClaudeCodeVersion`) are baked in with Vite's `define`, because the SDK is not installed where the runtime runs. **The runtime build ID is the SHA-256 of the file**; the runtime computes it from its own bytes, since a file cannot hold its own hash.

Note for whoever reviews dependencies: the bundle contains the SDK's code, which has its own license ("SEE LICENSE IN README.md" in its package), not k-bench's MIT.

### Launching: `agentCommand` in `src/server/claude.ts`

`TmuxDriver.createAgentSession(id, folder, launch)` starts the runtime as the Session's only program. The command is the same three-hop chain as a Claude TUI (`loginChain`): zsh with no startup files changes into the folder, the owner's login shell (`-l -i`) gives the owner's environment, and `/bin/sh` runs the Agent launcher with positional arguments only (never spliced into script text). The launcher resolves `claude` with `command -v` inside the login shell (the SDK needs an absolute path; a name with a slash is used as given), then **runs Node as a child, not with `exec`**, so it outlives the runtime and writes the `exit.json` gap record for an exit the runtime did not record. It is POSIX `sh`, so it runs under macOS's bash-as-sh and CI.

### Launch options

A Claude Agent takes the same Launch options as a Claude TUI, with the same meaning (#143). They are stored on the Session (`sessions.launch_options`), shared by both interfaces, and passed again at every start: `AgentRuntimes.launch` takes `options`, and Restart (`startStopped`) and Open in terminal reuse the stored ones.

- **To the runtime:** `agentLaunchArguments` (`src/server/claude.ts`) appends `--model`, `--effort`, `--advisor` and `--focus-view` to the runtime's command line after the launcher's seven positional arguments (Default adds nothing; the launcher does `shift 7` and passes the rest on as `"$@"`). `parseRuntimeArgs` reads them into `RuntimeArgs.launch`; a flag left out is Default.
- **To Claude Code:** `sdkLaunchOptions` (`src/agent-runtime/session.ts`) turns them into SDK options: `model`, `effort`, `extraArgs: {advisor}` (`--advisor <model>`) and `settings: {viewMode: "focus"}`. Advisor Off is `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1` in the environment the SDK gives `claude`. All of these are for that launch only: **never `/advisor <model>`, which saves the owner's default**, and nothing writes the owner's settings files.
- **In the Transcript:** Focus view is read back from the log, not from the Session: `buildItems` takes it from the latest `system/init`'s `view_mode` (`BuiltTranscript.focusView`, `transcriptInfo`, `useAgentConversation().focusView`), and `ToolCall` with `collapsed` shows a call as its one line (status mark, name, target), with no output or diff; the raw message has the rest.

## The server

- `src/server/agents.ts`, **`AgentRuntimes`**: everything the server does to an Agent. It keeps no state about a running Agent (tmux says what runs):
  - `install()`: copies the built runtime into `<dataDir>/runtimes/<build id>/` (once; content-addressed; through a temporary name), so a running runtime survives the app folder being replaced by an update (ADR-0007). It never throws: without a runtime only Claude Agents are unavailable (`current`, and `launch` says why). `current` is the build a new Agent starts on.
  - `pruneRuntimes(inUse)`: deletes the build folders (names of 64 hex digits, nothing else) that are neither `current` nor in `inUse` ([below](#updating-under-a-running-agent)).
  - `launch({sessionId, workspaceFolder, conversationId, mode})`: makes the Agent's folder (`0700`) and starts the runtime.
  - `connect(sessionId, stillWanted)`: the runtime's socket, retried until it listens; used by the relay and by the status connections (`AgentStatuses`, [State](#state-idle-working-waiting-for-you)).
  - `waitUntilReady(sessionId)`: the runtime's hello, or an `AgentStartError` carrying the reason it recorded. Creating an Agent waits for it, so the API answers once the Agent is running, and a failed start leaves no Session, tmux session or folder.
  - `isRunning`, `shutdown(sessionId)` (send `shutdown`, wait for the tmux session to go, kill it after four seconds), `removeFolder`, `removeStrayFolders(known)` (the reconciler's folder step, below), `readLog(sessionId)` (an `AgentLogReader`) and `stoppedReason(sessionId)` (the reason `exit.json` holds; if the launcher recorded an exit with no reason, "The Agent Runtime exited unexpectedly"; if there is no record, the Mac went down with it).
- `src/server/agent-sockets.ts`, **`AgentSockets`**: `GET /api/sessions/:id/agent`, behind the same access guard and Origin check as the terminal (`server.on("upgrade")` in `server.ts`). For each browser socket it opens one connection to the runtime's socket and forwards whole frames both ways unread. For an Agent that is not running it serves the Stopped Transcript instead (`stoppedAnswers`: `sync` and `page` from `AgentLogReader`, then `{type: "stopped", reason}`, everything else ignored). It closes with **4410** when the Session ended (not an Agent at all, or the runtime hung up while this socket was open and its tmux session went); a runtime that hung up while its Session is still running, or one that did not start, closes with 1011; a stopping server drops the socket with no 4410 so that the browser reconnects (#134).
- `service.ts`: `createSession(workspaceId, name, claude?: {options, interface})`; Claude Agent is `interface: "agent"`. Delete (of a Session or a Workspace) shuts the runtime down, removes the row, then removes the folder. `stopSession(id)` (`POST /api/sessions/:id/stop`, Agents only) is `agents.shutdown`: the Session stays, Stopped. Restart of a Stopped Agent (`restartSession`, whether from the row menu or the Stopped Pane's button) starts the runtime with `mode: "resume"` and the stored Launch options. `removeStrayAgentFolders()` runs once in `startServer`, after the orphan tmux sessions are killed and before any request, and deletes every `agents/<id>` folder with no Session row (a folder is made before its row, so this must not run on a live server). A Stopped Agent is never started by k-bench on its own: a crash, a Host restart and a k-bench restart all leave it Stopped. `getState()` adds `interface` for Claude Sessions.
- `store.ts`: `sessions.interface` (`tui` or `agent`, null for a shell; existing Claude Sessions became `tui`). The New Session dialog's remembered kind can be `claude-agent`; creating an Agent remembers its Launch options, the same ones as a Claude TUI's (one set, shared by both).
- `config.ts` / `ServerOptions.agentRuntimeFile`: the built runtime to install. `main.ts` passes `dist/runtime/agent-runtime.mjs` relative to its working directory, as it does `dist/web`. It is an option, not an instance setting, so a test can start a server on a second runtime build (#158).

## The browser

- `web/src/agentConnection.ts`: `createAgentConnection({sessionId, openSocket})`, no React: opens the socket and keeps it open, the same shape as `terminalConnection.ts`: when it drops it reconnects with backoff (`retryFirstMs` 500, doubling to `retryMaxMs` 5000), and at once when `wake` fires (the page became visible, the browser went online: `retryWhenAwake`). Every socket it opens starts with `sync` from the newest entry it has had (`lastSeq`), so across any number of drops the listener gets each entry once. It reports `message`, `reconnecting(on)` and `ended` (a close with 4410, never retried). `send` returns whether the command was sent or kept: while reconnecting it is dropped, never queued, so a prompt cannot go out late; the Composer disables Send and keeps the text meanwhile, and the Pane says "Reconnecting…". Closing a tab, a device sleeping and k-bench restarting only end a connection: the runtime never notices.
- `web/src/agent/transcript.ts`: what the conversation holds, and how messages go in: `applyServerMessage(state, message)` keeps the log entries and the live fragments, and `transcriptItems(state)` gives the items to show (what `buildItems` makes of the entries, then the streaming ones). - `web/src/agent/items.ts`, `toolDisplay.ts`, `activity.ts`: the Transcript's rendering rules, [below](#the-transcript).
- `web/src/agent/useAgentConversation.ts`: the hook the Pane uses: `{items, entries, asks, header, hello, state, mode, turnStartedAt, context, commands, ended, stoppedReason, reconnecting, send, answer, cycleMode, interrupt, interrupting, history}`.
- `web/src/components/agent/`: `AgentPane` (the header, the conversation, `role=log`, the status line), `Transcript` (the items, each in a `RawMessage`), `AgentHeader`, `StatusLine`, `PromptDock` (what is under it: the input, or, while Claude waits on an ask, `PermissionPrompt`, the docked permission panel built from the shared `AskPanel` parts (frame, numbered `Choice`, `useAnswerGate`), with the input only hidden so a half-typed message survives; `AskDock` chooses it by tool name: `QuestionPrompt` for AskUserQuestion, `PlanPrompt` for ExitPlanMode, built from the same parts plus `ReplyBox`, the feedback box that `PermissionPrompt` and `PlanPrompt` share), `Composer` (the input). A Claude Agent never gets Extra keys or Smart typing (`usePaneView.focusedHasTerminal`). `Pane.tsx` switches on `session.kind === "claude" && session.interface === "agent"`; `SessionRow` shows a speech bubble and keeps the Claude spark.
- Accessible names tests across tickets rely on (keep them stable): the Pane region `Claude Agent <name>`, the conversation `Conversation` (`role=log`), the input `Message Claude`, the buttons `Send` and `Interrupt` (the latter only while Claude works), the permission card, a region `Permission prompt` with the numbered buttons `1. ### The raw view (#137) and its seam

The raw JSON of any message is the fallback whenever something renders wrongly, and the place an Unsupported row (#153) sends the owner. It is browser-only and holds nothing but display state.

- **What "raw" is** (`web/src/agent/raw.ts`, `rawOf(entry)`): for an `sdk` log entry, the SDK message **exactly as Claude Code sent it**, with no `seq`/`t`/`kind` wrapper (the runtime logs it unchanged, so this is the original, indented for reading). For any other kind (`prompt`, `permission_asked`, `runtime`...), k-bench's own record, which is the entry itself. Live `stream_event` fragments are never logged and have no raw.
- **The seam is the entry's `seq`.** Every `TranscriptItem` built from a log entry carries that entry's `seq` (`item.seq`; text still streaming has none). A new item kind (#136's reshaped items, #148, #153...) **must set `seq`** from the entry it comes from, or its message offers no raw. A row built from several entries sets the one the owner would call "the message". `useAgentConversation` returns `entries` (the log entries received) so the Pane can find the entry of an item.
- **The UI** is `components/agent/RawView.tsx`. `useRawView()` holds the choices for this device (`all`, `isShown(seq)`, `show(seq)`, `toggle(seq)`); `RawMessage` wraps a row and adds `</>` on desktop (on hover or keyboard focus) or a long-press on a phone (a touch held 500 ms without drifting 10 px, so a scroll or a tap is not one), which shows the JSON under the row and, again, hides it; `RawSwitch` is the header's `Raw` checkbox; with it on, `RawTranscript` replaces the conversation with every entry's JSON in order, including entries no row shows, and off brings the conversation back.
- **An Unsupported row opens it** with `useShowRaw()(item.seq)`, the `onShowRaw` of the spec; `AgentPane` provides it (`ShowRawProvider`) around the conversation's rows. It shows that message's raw JSON under the row, the same as the `</>`. A row that renders several blocks of one entry shows the JSON under each block of it.

## The Transcript

The conversation in Claude TUI's shape ([#136](https://github.com/k-electron/k-bench/issues/136)). The browser makes it from the raw SDK messages in the log, every time, so a display fix reaches even a long-running Agent on the next page load. Later tickets add to it by the seams below, in new files rather than by growing these.

- **Entries to items: `buildItems(entries)` in `web/src/agent/items.ts`.** Pure, one pass over the log. The items (`TranscriptItem`, a union on `kind`): `permission` (`⎿ permission: allowed`, `allowed, and won't ask again`, `denied` or `denied: <reply>`; for questions and plans the same item with another `topic`, [Questions and plans](#questions-and-plans); made from each owner-answered `permission_answered` entry where it was logged, so it reads the same on every device; an ask nobody answered leaves none), `prompt` (`>` in a band, with `(queued)` until Claude Code has picked it up: `prompts.ts`, #138), `assistant` (`⏺` and markdown), `thinking` (one muted line, with its duration from the frame's `thinking_duration_ms`), `tool` (`⏺ Name(target)` and its result under `⎿`) `interrupted` (`⎿ Interrupted`) and `command_output` (what a typed command answered, [below](#the--menu-and-typed-commands)). Each carries a stable `key` and, unless it is still streaming, the `seq` of the entry it came from (what the Raw view, #137, shows for it: `Transcript` wraps every item in a `RawMessage`). **To show a new kind of thing:** add its interface and put it in the union; make it in `buildItems` (`readSdkMessage` for an SDK message, the switch for the other kinds of entry); add a case in `TranscriptItemView` (`components/agent/Transcript.tsx`), where a `never` check fails to compile until there is one. A message type `buildItems` knows but does not read shows nothing. One it does not know is an `unsupported` item ([below](#unsupported-rows)).
- **`/goal` and `/loop`: `web/src/agent/goal.ts` (#152).** `readGoalMessage`, called from `readSdkMessage` before the less common reader, makes two items: `goal-set` (`◎ Goal set: <condition>`, article `Goal set`) from the synthetic assistant message (`model` is `<synthetic>`) that starts "Goal set:", and `goal-check-in` (`⎿ Goal check-in: <feedback>`, article `Goal check-in`) from every user message whose text starts "Stop hook feedback:". The check-in is decided by its text **before** the `isSynthetic` and `isReplay` branches of the `user` case, because those would drop it or show it as the owner's prompt, and the live check did not record which flags the real message carries. A `/goal` is one turn with one `result`, so nothing else about it is special: the runtime sees an ordinary turn. `/loop` has no reader at all: a turn Claude Code starts by itself is made of ordinary messages, which show like any turn with no prompt before them; the runtime counts it as Working and raises the Bell when it ends unseen ([State](#state-idle-working-waiting-for-you)). The loop dies with the runtime. The fake scripts `/goal` with `raw` steps (`e2e/claude-agent-goal-loop.spec.ts`).
- **The less common lines: `web/src/agent/uncommon.ts` (#148).** Its own module, called from `buildItems` at two points: `readUncommonMessage` for every top-level SDK message (after the subagent check) and `readUncommonBlock` for every block of an assistant message. Each returns whether it **handled** the message (`items.ts` then reads no further); a message handled with no line (a hook that printed nothing, a rate limit that says all is well, `hook_started`) is still handled. The Unsupported rows (below) go by the tables in `unsupported.ts`, which already list every message, subtype and block read here, so none of these is ever an Unsupported row; a new kind added here must be in those tables too. `init` and `result` return false after adding what they add, because `items.ts` still reads the model, the folder and the tools left running. The kinds, each an `article` (`components/agent/UncommonLine.tsx`, one case group in `TranscriptItemView`):

  | Kind         | Made from                                                                                                                                                                                                                                                                                                                  | Name                                                                                                  |

  The same text said twice in a turn (the reply with an `error`, then the `result` that repeats it) is one line, and a usage limit said by both the rate limit event and the reply is one line in Claude Code's own words. Of these, the advisor's frames and a hook's response were recorded from a real Claude Code (`test/harness/fixtures/uncommon-messages.json`); the others are shaped from the SDK's types and have not been seen live.
- **What the rules are.** A prompt k-bench sent is shown from its `prompt` entry (there is no echo until Claude Code picks it up), and the echo with the same `uuid` is not shown again; an echo k-bench did not send (typed in the terminal, imported) is shown as a prompt. A tool call is paired with its `tool_result` by `tool_use_id`: no result yet is **running** (a spinner), a result is **done** (green), and red is **denied** (the owner's `deny` in the log, or Claude Code's `permission_decision` of `reject`), **interrupted** (Claude Code says so in the result, or the turn's `result` message, or a runtime start or stop, came with the call still without one) or **failed** (`is_error`). A call that was interrupted has no result line of its own, only the red mark: the `Interrupted` line the interrupt leaves says it once. A subagent's own messages (`parent_tool_use_id`) are not shown as lines (an Unsupported one still is): its task shows how it goes ([Subagents and background tasks](#subagents-and-background-tasks)).
- **Tool wording: `web/src/agent/toolDisplay.ts`.** `toolTarget` (the part in parentheses: a Bash command, a path relative to the turn's `cwd`, a pattern, a URL), `toolDisplayName` (an MCP tool as `server - tool (MCP)`), `toolDiff` (an edit's lines, from Claude Code's `structuredPatch` when its result has one, else from the input's `old_string`/`new_string`, a `Write`'s content as added lines), `toolResultView` (the `⎿` summary and output lines). They take only the tool's input where they can, so the permission panel (#146) can show the same target and diff before the tool has run. A tool not named there gets the generic reading, so a new Claude Code tool still shows.
- **Components, one per concern:** `Transcript` and `TranscriptItemView` (the switch), `ToolCall` (status mark, result, diff), `Markdown` (react-markdown with GitHub tables and task lists, no raw HTML; a development dependency, bundled into `dist/web`), `Diff` (`<ins>` and `<del>` lines, scrolling sideways inside its box), `ExpandableLines` (the collapse: five lines of output, twenty of a diff, "+N lines, tap to expand"; reuse it for any long run of lines), `AgentHeader`, `StatusLine`. Items and their components are memoised, and `transcriptItems` rebuilds the log's items only when entries arrive, so a stream of fragments re-renders only what is streaming.
- **Header and status line.** The header is `claude <version> · <model> · <folder>`: the version from `hello`, the model from the latest `system/init`, and the folder from `init.cwd`, or `hello.folder` before it. Claude Code sends `system/init` at the start of **every turn**, not at process start, so before the first prompt the model is left out. The status line shows `✻ <activity>… (<n>s)` while the Agent is Working (`status.state`, `turnStartedAt`; activity is read from the end of the items by `currentActivity`), `✻ Waiting for you (<n>s)` while it is Waiting, and goes when the turn ends. It also shows `Context left until auto-compact: N%` whenever Claude Code has reported it, because that is what is glanced at between turns. The percentage is worked out in the browser (`contextLeftPercent`: what is left of `autoCompactThreshold`, read as tokens, after `totalTokens`), so if that reading is wrong the fix is a display fix. `turnStartedAt` is the runtime's clock: the seconds are clamped at zero, and a device whose clock differs from the Host's shows them off by the difference.
- **Accessible names** (keep them stable; tests across tickets use them): the header `note` "Claude Code"; each item an `article`: "Your prompt", "Claude", "Thinking", "Command output", and for a tool "`Name(target)`"; the tool's state an `img` named "Running", "Done", "Denied", "Interrupted" or "Failed"; an edit's diff a `figure` "Diff of `target`" with `insertion` and `deletion` lines; the expand button "+N lines, tap to expand" (then "Show fewer lines"; `aria-expanded`); the status line a `status` "Claude status", and the context a `note` "Context left". The glyphs (`>`, `⏺`, `⎿`, `✻`) are `aria-hidden`.

### Unsupported rows

Whatever a Claude Agent meets that k-bench can't show or answer becomes an `unsupported` item where it happened (#153): `⚠ Unsupported.`, what Claude tried in plain words, and an `Open raw view` button (`UnsupportedRow`, calling `useShowRaw()(item.seq)`). It raises no Bell: only a turn's end and an ask do, in the runtime. The row also has Open in terminal (`OpenInTerminalProvider`, [below](#open-in-terminal)).

- **What counts, and where it is found** (`web/src/agent/unsupported.ts`, pure; `buildItems` makes the items). An item has `what`, `name` and `summary`, and **`unsupportedKind(item)` is `what:name`**, the string the running list (below) counts by (the same thing again is the same kind, in any Session):
  - `message:<type>`, `system:<subtype>` and `block:<type>`: a top-level message type, a `system` subtype or a content block type that is in none of the tables in that file. The tables are what the browser **recognises**: a kind a later ticket starts to show (#148, #149, #152) stays in its table, because recognised is not the same as shown. They hold every message of the SDK this was built against, so the news is a newer Claude Code growing something. A subagent's unknown message counts too.
  - `declined:elicitation`: a `declined` log entry. The runtime sets the SDK's `onElicitation` (`session.ts`) to answer `{action: "decline"}` and record what was asked; without it the SDK declines by itself and nothing is left to show. Other dialogs (`onUserDialog`) are left unset, with `supportedDialogKinds`, so Claude Code does not emit them. A later dialog the runtime declines adds a `what` to the `declined` entry and a case in `unsupportedOfDeclined`.
  - `command:/name`: the reply of a command that is not available here ("isn't available in this environment"), **found by that text**, in a `system/local_command_output`, a user message's `<local-command-stdout>`, or an assistant message that is only the reply (prose that merely says the words is Claude's). The live check (#161) recorded the assistant one (model `<synthetic>`, `local_command_source`, `local_command_outcome: {kind: "unavailable_headless"}`); the others are still read. #150's rows for command replies must leave an unavailable one to this row.
  - `terminal-command:/name`: a prompt that starts with a command Claude Code lists in `system/init.terminal_slash_commands` (which comes with the turn's `init`, after the prompt). The row's raw is that `init`; a command that also answers "isn't available" is still one row.
- **The running list (#154).** `useReportUnsupported` (`web/src/agent/reportUnsupported.ts`, called by `AgentPane`) tells the server about each `unsupported` item that comes from a log entry, once per occurrence (`POST /api/unsupported`, see [the API](api.md)); the occurrence is `<sessionId>:<seq>:<kind>`, so two devices (or a reload) showing the same row count once, and it is reported when a Pane shows the row, not when it happens. The server keeps it in the store (`unsupported_kinds`, plus `unsupported_occurrences` to dedupe, which go with their Session); clearing deletes the kind's row. It is read in the sidebar's **Unsupported** dialog (`UnsupportedListDialog`), when opened and on window focus; it is not part of the state snapshot, so it does not update live.
- **Wording** is in `unsupported.ts`, so a fix to what a row says is a display fix that reaches the whole history.
