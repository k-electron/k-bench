# The API

The API so far. Every request needs the login described in [Access](access.md).

- `GET /api/health`: `{ "status": "ok" }`. What `k-bench status` asks; guarded like every other route (it needs the owner's login).
- `GET /api/state`: Workspaces with their Sessions (`kind`, `"shell"` or `"claude"`; for a Claude Session, `interface`, `"tui"` or `"agent"`; `running` or `stopped`; and `bell`). The Launch options and the conversation ID of a Claude Session are not in it.
- `POST /api/sessions/:id/restart`: starts a Stopped Session again in its Workspace folder, same id and name (a running Session is left alone; 422 when the folder is gone, for either kind). A Claude Agent starts a new Agent Runtime on the same log and resumes its Claude conversation (or starts it, when no prompt was ever sent), answering once it is up. A shell Session gets a fresh shell. A Claude Session resumes its Claude conversation: Claude Code is run with `--resume <conversation ID>` and every stored Launch option again, since `--resume` does not restore `--settings`. Claude Code saves a conversation only after its first message, so when the owner quit without sending one, `--resume` fails with exit 1 and the launcher runs `--session-id <conversation ID>` with the same options instead. That cannot fork or overwrite a conversation, because `--session-id` fails with exit 1 on an ID that already has one. k-bench decides by exit statuses alone and never reads Claude Code's files (ADR 0005). If both attempts fail, the error hold below applies. There is no dialog and no request body.
- `GET /api/directories?path=`: the subfolders of `path` (default: the configured picker root) for the folder picker; 422 if the path is not an existing absolute folder.
- `POST /api/workspaces` `{folder, name?}`: the name defaults to the folder name, with a "(2)"-style suffix when taken; an explicit name that is taken gets 409, a missing folder 422.
- `POST /api/workspaces/:id/sessions` `{name?, claude?, interface?}`: creates a Session (201 `{id, name}`). Without `claude` it is a shell Session, unless `interface` is `"agent"` (below). With `claude` (an object; 422 otherwise) it is a Claude Session: k-bench generates its conversation ID and starts Claude Code in the Workspace folder through the owner's login shell with `--session-id <conversation ID>`. The Launch options are `claude: {model, effort, advisor, focusView}`; a field left out is Default. An unknown value, or a `claude` that is not an object, gets 422 naming the field (`claude.model`), and no Session is created. k-bench does not check which model and advisor go together: Claude Code rejects a bad pairing, and the error hold below shows its message. The Launch options are stored with the Session, and a restart passes them again. "Default" passes no flag, so the owner's own Claude Code settings apply.
  - `model`: `default`, `fable`, `opus`, `sonnet` or `haiku`, passed as `--model <alias>`.
  - `effort`: `default`, `low`, `medium`, `high`, `xhigh` or `max`, passed as `--effort <level>`.
  - `advisor`: `default`, `off`, `fable`, `opus` or `sonnet`, passed as `--advisor <alias>`. `off` passes no flag (there is none) and sets `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1` for that launch only.
  - `focusView`: a boolean. `true` passes `--settings '{"viewMode":"focus","tui":"fullscreen"}'` (both keys, because focus view needs the fullscreen renderer). It applies to that launch only and leaves the owner's Claude Code settings files unchanged.

  `interface` is `"tui"` (the default, Claude Code in a terminal, as above) or `"agent"`, a Claude Agent: the Session runs an Agent Runtime in a hidden tmux session, and its conversation is the agent WebSocket below. `"agent"` makes it a Claude Session even without `claude`, which is then all Default (a Claude Agent takes no Launch options yet, and creating one does not change the remembered Launch options); `"tui"` without `claude`, or any other value, gets 422. The response comes once the runtime is up and has said hello. If it cannot start (the runtime is not built, `claude` is not found or fails to start), the response is 422 `Claude Agent could not start: <reason>` and no Session, tmux session or Agent folder is left. See [Claude Agent internals](agent.md).

  Claude Code quitting with status 0 makes the Session Stopped; with another status the pane keeps the error on screen ("Claude Code exited with an error. Press any key to close.") until a key is pressed, then the Session is Stopped. A blank name gives "session N", a taken name 409, a Missing Workspace 422.
  Creating a Session also records its kind on the Host, and a Claude Session its Launch options, each in a one-row table of its own, replacing the last ones (a refused creation records nothing; the name is never recorded). There is no write endpoint.
- `GET /api/new-session/last`: what the New Session dialog opens on, as `{kind, claude}`. `kind` is the kind of Session created last (`"shell"`, `"claude"` for a Claude TUI, or `"claude-agent"`; `"shell"` when none has been). `claude` is the Launch options last used to create a Claude Session, as `{model, effort, advisor, focusView}`; all `"default"` with `focusView` false when none has been created. Creating a shell records only the kind, so the Launch options are kept for the next Claude TUI. The dialog reads it each time it opens, so every device opens on the same choices. Both survive a k-bench restart.
- `PATCH /api/workspaces/:id` `{name?, folder?}`: rename and/or change the folder; 409 for a taken name, 422 for a blank name or a folder that does not exist (neither change is made if one is refused), 404 for an unknown Workspace.
- `PUT /api/workspaces/order` `{ids}`: the full ordered list of Workspace ids (422 unless it is every Workspace exactly once).
- `DELETE /api/workspaces/:id`: ends every Session's shell (a Claude Agent's runtime is shut down first), then removes the Workspace and each Agent's folder (204). The folder on disk is never touched.
- `PATCH /api/sessions/:id` `{name}` renames a Session (409 if the name is taken in its Workspace, 422 if empty); `DELETE /api/sessions/:id` ends its shell and removes it (204); for a Claude Agent it shuts the runtime down (killing its tmux session if it has not exited after four seconds), removes the row, then removes the Agent's folder. Session names are unique per Workspace; created without a name, a Session gets "session N" with the next free N.
- `GET /api/sessions/:id/terminal?cols=&rows=` (WebSocket): output arrives as binary frames; input and resizes go out as JSON text frames, and close code 4410 means the terminal has ended (the Session was deleted, or is Stopped), so the client must not reconnect. The protocol is defined once, in `src/shared/terminal-protocol.ts`, which the server, the browser and the tests all import. Input the terminal sends by itself (answers to tmux's queries) is marked `automatic`, so it never takes the window's size for its device.
- `GET /api/sessions/:id/agent` (WebSocket): a Claude Agent's conversation, one per open Pane, behind the same access guard and Origin check as the terminal. The server opens one connection to the Agent Runtime's unix socket for each browser socket and forwards whole JSON text frames both ways without reading them. The protocol (hello, `sync`, `prompt`, entries, fragments) is defined once, in `src/shared/agent-protocol.ts`, and described in [Claude Agent internals](agent.md). Close code 4410 means the Session ended (it was deleted, it is Stopped, or it is not a Claude Agent), so the client must not reconnect; 1011 means the Agent did not answer, and the client may try again. A stopping server drops the socket with neither.
- `GET /api/events` (WebSocket): sends the full state (same shape as `GET /api/state`) as a JSON text frame on connect and again whenever it changes, whether from a request on any device or from something tmux-side such as a shell exiting. Clients send nothing. Each frame also carries a `revision`, and every successful change request answers with a `State-Revision` header: a client waits for a snapshot at that revision or later to see its change. The snapshot shape, the header name and the decoding are defined once, in `src/shared/state-protocol.ts`; the browser's `web/src/stateClient.ts` is the client. A running Claude Agent's Session carries `agent`: `{state, turnStartedAt?, claudeVersion?, runtimeBuildId?, tasks?}`, where `tasks` lists the subagents and background tasks running now (`{id, kind: "subagent" | "background", description}`, in the order they started; absent when none, and they outlive turns, so an Idle Agent can have some), and where `state` is `idle`, `working` (a turn is running, whoever started it) or `waiting` (an Allow/Deny ask is open, the owner's Waiting for you), `turnStartedAt` is when the running turn began (milliseconds since the epoch, the Host's clock), and the two versions come from the runtime's hello. A Stopped Agent has no `agent` (its `status` is `"stopped"`), and neither has one whose runtime the server has not heard from yet, which the browser shows as any running Session. The server reads it from one status connection per running runtime ([Claude Agent internals](agent.md#state-idle-working-waiting-for-you)) and announces every change on this socket at once.
