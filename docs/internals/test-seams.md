# Test seams

[docs/testing.md](../testing.md) says what a good test is here and how to write one. This page describes the three harnesses tests go through: Seam 1, the server's HTTP/WebSocket API with Vitest; Seam 2, the browser with Playwright; and Seam 3, the packed `k-bench` command run as a process, also with Vitest. Run them with `pnpm test` (Seams 1 and 3) and `pnpm test:e2e` (Seam 2); Playwright needs its browsers once (`pnpm exec playwright install chromium webkit`).

## Seam 1: the server (Vitest)

Tests live in `test/`; the harness is in `test/harness/`.

- `createTestInstance()` gives an isolated instance (temp data folder, unique `kb-test-*` tmux socket) that is cleaned up after each test.
- `instance.start()` boots the real server in-process and can be called again after `stop()` to simulate a restart (`{ statePollMs }` lengthens the state poll, so a test can tell a pushed change from a polled one).
- Every request and upgrade carries the instance's configured login in `Tailscale-User-Login` by default. `server.as(login)` and `server.anonymous()` give views that send another login or none, `server.withHeaders({origin, host})` adds headers such as a page's `Origin`, and `server.upgradeStatus(path)` reports the status refusing an upgrade.
- `server.openEvents()` returns an `EventsClient` (collected snapshots, `waitForSnapshot()`).
- `instance.openStateClient({ showTimeoutMs })` builds the browser's state client (`web/src/stateClient.ts`) over a `ws` WebSocket carrying the login header (`server.openEventsSocket()`), since Node's built-in WebSocket can't send one. It follows the instance across `stop()` and `start()`, so a test can watch it reconnect to a restarted server; read `client.state`, wait with `client.whenShown({ revision })`, where `revision` is `revisionOf(response.headers)` from `src/shared/state-protocol.ts`, and call `client.resync()`. It is closed with the instance.
- `instance.openTerminalConnection(sessionId, { size, retryFirstMs, retryMaxMs, wake })` builds the browser's terminal connection (`web/src/terminalConnection.ts`) over a `ws` WebSocket carrying the login header (`server.openTerminalSocket(path)`), with backoff of a few milliseconds by default (`wake` stands in for the page becoming visible or online: a test keeps the `retry` it is given and calls it). Like the state client it follows the instance across `stop()` and `start()`, and is closed with it. It returns a `TerminalConnectionProbe` (`test/harness/terminal-connection.ts`): `run()`, `waitForOutput()`, `output`, `reconnecting`, `ended` and `socketsOpened`, with the connection itself as `.connection`.
- `server.openTerminal()` returns a `TerminalClient` with `run()`, `resize()` and `waitForOutput()`.
- `server.createClaudeSession(workspaceId, { name?, claude? })` creates a Claude Session (it sends `claude: {}` unless given Launch options).
- No test runs the real Claude Code. The Claude Code boundary is a stub, `test/harness/fake-claude.sh`, a plain `sh` script (it runs under the bash 3.2 of the CI runner). `createTestInstance()` copies it, with its own `conversations` folder beside it, into the instance's temp folder (`installFakeClaude()` in `test/harness/fake-claude.ts`) and sets the instance config's `claudeProgram` to it. The tmux server's environment is not the test's, so the stub is configured by where it lives, not by environment variables. Override `claudeProgram` in `createTestInstance({ claudeProgram })` to test a program that is missing.
  - On start it prints `claude-stub cwd: <folder>`, `claude-stub advisor tool disabled: <value or unset>` and one `claude-stub arg: <argument>` line per argument, then `claude-stub ready`. `fakeClaudeArgs(terminal)` waits for it and returns the arguments of the attempt that started (a restart that finds nothing to resume shows the failed `--resume` attempt too, then the `--session-id` one that started). The flags that reach the stub are the contract with Claude Code, so asserting on them checks a boundary.
  - Like Claude Code it saves a conversation only once a message has been typed into it (any line but the two below), and answers `claude-stub heard: <message>`. `--resume` of an ID it never saved, and `--session-id` of one it saved, each fail with exit 1.
  - `exit N` makes it quit with status N, and `bell` rings the terminal bell.
- The same stub also stands in for Claude Code under the Agent SDK. Started with `--input-format stream-json`, as the SDK starts it, `fake-claude.sh` hands over to `fake-claude-sdk.mjs` (plain JavaScript, run by a `node` link `installFakeClaude()` puts beside it) and stays out of the TUI behaviour above. The real `@anthropic-ai/claude-agent-sdk` (a development dependency, pinned exactly; Dependabot gives it a pull request of its own) drives it, so an SDK upgrade that changes the protocol breaks `test/fake-claude-sdk.test.ts` in that pull request, which is the point. See [The fake for the Agent SDK](#the-fake-for-the-agent-sdk).
- Sessions run the owner's real login shell, but each instance gives its shells a `ZDOTDIR` of their own (a hidden folder in the instance's temp folder, set in this process's environment, which the tmux server inherits) whose `.zshrc` only unsets `HISTFILE`. So test shells read neither the owner's `~/.zshrc` nor `~/.zsh_history`, and keep no history. Shared, zsh's history-file lock made shells starting while others exited wait up to 10 seconds, and test commands landed in the owner's history.
- `pollUntil()` waits for outcomes.
- `test/harness/tmux.ts` kills a test instance's tmux server (a Host reboot), plants a tmux session the store does not know, lists the socket's sessions, counts its running tmux client processes, types into a Session with no terminal attached (`typeIntoSession`, how tests ring a Bell nobody watches) and counts the clients attached to a Session (`attachedClientCount`). It refuses any socket not named `kb-test-*`.
- `test/harness/attachments.ts` boots an `Attachments` module over a running Session on a test socket, with a `RecordingViewer` and a Session lookup the test can hold pending, for the terminal-lifecycle races the WebSocket cannot time.

### Claude Agents

A Claude Agent test drives a real k-bench server, which starts the **real Agent Runtime, with the real Agent SDK inside it**, in its hidden tmux session, pointed at the fake `claude` below. Nothing is mocked between the API and the fake.

- **The runtime build.** `buildAgentRuntime()` (`test/harness/agent-runtime.ts`) builds the runtime once per run, unless the file is newer than its sources, into `node_modules/.cache/k-bench/agent-runtime/agent-runtime.mjs` (`HARNESS_RUNTIME_FILE`). **Both global setups call it**, Vitest's (`test/harness/global-setup.ts`) and Playwright's (`e2e/global-setup.ts`), because both start servers that start Agents. It is not `dist/runtime`, which `pnpm build` (the packed test runs it) rewrites. `instance.start()` installs the harness build; `instance.start({ agentRuntimeFile })` installs another, for a test of an update under a running Agent (#158).
- `server.createClaudeAgent(workspaceId, { name?, claude? })` (Launch options, fields left out Default) creates a Claude Agent and returns once its runtime is up. `server.openAgent(sessionId)` returns an `AgentClient` (`test/harness/agent.ts`) connected to the agent WebSocket with the login header, like a browser's Pane: `hello`, `messages`, `entries` (replayed and live, in order), `fragments` (streamed text), `assistantTexts`, `closeCode`; `snapshots` (the text-so-far messages) and `lastSeq` (what a reconnecting client syncs from); `await sync(afterSeq?, {tailTurns?})` asks for the replay (with `tailTurns`, only the latest turns, as a fresh page does; `replayFrom` says where they begin, and `await page(beforeSeq, limit)` fetches the turns before, as scrolling up does; pages are not among `entries`) (nothing but hello and status arrives before it; fragments are never replayed, but a sync mid-reply also brings a snapshot of the text so far, so sync before sending a prompt from another connection if you want its fragments one by one). A server restart is `await server.stop()` then `instance.start()`, whose new server opens new clients; the runtime, a process of its own, carries on through it, `prompt(text)` returns the ID it sent, `sendRaw(text)`, `waitForEntry(check, description)`, `waitForClose()`; for permission asks, `openAsks` (asked and not answered, as far as the client knows), `waitForAsk()` and `answer(requestId, "allow" | "deny")`. `interrupt()` sends an interrupt. `status` is the newest status received (`state`, `turnStartedAt`, `context`). `isResult` finds the entry that ends a turn.
- Script the turn with `instance.fakeClaude.script([...])` **before** sending the prompt, and read what Claude Code received with `fakeClaude.prompts()` (text as typed, and the `uuid` the client set) and `fakeClaude.received()` (each start's `argv`, `cwd` and the SDK's environment: `--resume=`, `--session-id=`, `--replay-user-messages`, `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING`). A `{ hold }` step is how a test sees a fragment while the turn is still going.
- Simulate a Host going down with `killTmuxServer(socket)`: the runtime gets SIGHUP and shuts down cleanly, and the Session is Stopped.
- Do not assert on the log file, the socket or tmux commands: what a test may rely on is the Agent folder's existence and mode (`agentFolder()` in `src/agent/paths.ts`), that it is gone after a delete, and what comes over the socket.

### The fake for the Agent SDK

`test/harness/fake-claude-sdk.mjs` speaks what the SDK's stdio protocol has Claude Code speak, from the `initialize` handshake on, so tests of a Claude Agent run with no model turn and no login, in CI.

- **Handshake and control.** It answers `initialize` (the account, `claude_code_version`, commands and models `initializationResult()`, `accountInfo()` and `supportedCommands()` read), `interrupt`, `set_permission_mode`, `set_model`, `get_context_usage` (the `contextUsage` setting, or `null` for a Claude Code too old to know it) and the other requests the SDK makes with an empty success, and anything else with the `error` an older Claude Code sends. It exits 0 when the SDK closes its stdin and 143 on SIGTERM, exits 1 for `--resume=<id>` of a conversation it never saved and for `--session-id=<id>` of one it did (the SDK spells flags with `=`), and can crash on cue.
- **A turn** (one per prompt) is `system/init`, the prompt echoed back when `--replay-user-messages` is set, then the scripted steps as `stream_event`s with one `assistant` message per content block, `user` tool results, and a `result`. `command_lifecycle` (`queued` when a prompt arrives, `started`, `completed`) and `session_state_changed` (`running`; `requires_action` while a permission ask waits; `idle` when nothing is queued) go out as the real one's do. A turn nobody scripted answers `fake claude heard: <prompt>`; a prompt `/clear` takes no script and resets the conversation as Claude Code does, with no turn (`conversation_reset` with a decoy `new_conversation_id`, then an `init` with a new `session_id`, the only one with a saved conversation).
- **Steering it.** `createTestInstance()` gives `instance.fakeClaude` (`FakeClaude` in `test/harness/fake-claude.ts`), which writes files the fake reads, since the fake runs as a process of its own. `configure({ account, version, plugins, commands, terminalSlashCommands, model, contextUsage, initFields, sessionStateMessages })` says what it is (`sessionStateMessages: false` stops it sending `session_state_changed`, as a Claude Code that does not would; `userSettingsFile` names the test's stand-in for the owner's user settings, which a `/advisor <model>` prompt overwrites as the real command does, so a test can show a Launch option never reaches it). `script(steps)` scripts the turn the next prompt takes (oldest first), `spontaneous(steps)` a turn nobody sent, as `/loop` causes, that starts by itself once the fake is idle, and `release(name)` lets a turn waiting at `{ hold: name }` go on. The steps (`FakeStep`) are streamed `text` (a sentence, or fragments, which may include a `{ hold }` to stop part-way), `thinking`, `tool` (optionally with `ask`: a permission request, `AskUserQuestion` and `ExitPlanMode` included, which waits for the SDK's answer; or with `hold: name`: a tool still running, with no result until `release(name)`, and an interrupt ends the turn with it unanswered), `hold` (until released or interrupted), `raw` (any message, such as a type the browser does not know), `elicit` (an MCP server asks the owner for input: the turn waits for the SDK's answer, which `received()` holds as a `control_response`), `system` (any `system` subtype), `mode` (Claude Code changes its own permission mode and says so in `status`), `reset` (`/clear`), `result` (fields of the final `result`) and `exit` (a crash with an exit code and stderr). An interrupt ends the turn the way Claude Code does.
- **Subagents and background tasks** (#149). The fake keeps the tasks it started, by id. A `tool` step with `task: {id, description, type: "agent" | "bash", background}` is a subagent (`Agent`) or a background command (`Bash`): `task_started` carries the tool call's `tool_use_id`, as the real one's does. A foreground task blocks the tool call and ends (`task_updated`, `task_notification`) before its result; a `background` one is also in `background_tasks_changed` (the full list, which replaces) and goes on after the result and the turn. A `{ task }` step starts one with no tool call, `{ taskProgress }` sends `task_progress` and `{ taskEnd }` ends one, and `fakeClaude.endTask(id)` ends one from outside any turn, as a background command finishing does. `fakeClaude.say(message)` sends any message outside any turn (a background subagent's own frames arrive after the turn that started it). The SDK's `stop_task` ends only the task it names, with a `task_notification` of status `stopped`; an id that is not running is an error. An interrupt ends the foreground tasks and leaves the background ones. **Unlike the rest of the fake these shapes are from the SDK's types, not recorded** from a real Claude Code (the live check, #161, should confirm them).
- **What it received.** `fakeClaude.received()` lists, in order, what the fake started with (`start`: pid, folder, every argument and the few `CLAUDE_*` variables the SDK sets (and `CLAUDE_CODE_DISABLE_ADVISOR_TOOL`), never the whole environment, so a test can assert on `--model=`, `--effort=`, `--advisor`, `--settings`, `--resume=` and the checkpointing variable), each prompt with the `uuid` the client gave it, each control request and control response (the answer to a permission request is one), the interrupt, and the close. `prompts()` and `waitForReceived()` read it.
- **Test it with the real SDK**, as `test/fake-claude-sdk.test.ts` does: `query()` with `pathToClaudeCodeExecutable` set to `instance.config.claudeProgram`, and an explicit `env` so the test run's own `CLAUDE_CODE_*` variables do not leak in.

**Recorded, not invented.** Every message the fake sends is a real one with the values a test chose filled in: `test/harness/fixtures/messages.json` holds one example of each kind (`initialize` reply, `init`, stream events, assistant frames, permission asks, tool results, `result`, an aborted turn, `conversation_reset`, ...), recorded from Claude Code 2.1.327 through SDK 0.3.325 on Haiku. What the recording showed that a later ticket may rely on:

- A prompt sent while a text-only reply was streaming (a send during a tool-using turn was not recorded: Claude Code may fold it into the running turn between tool rounds, naming it in `user_message_uuids` on later frames, so the queued mark accepts every pickup signal, see [Interrupt and queued prompts](agent.md#interrupt-and-queued-prompts); the fake always runs it as a turn of its own) was not folded into it. Claude Code finished the reply (`result`), then ran the prompt as a turn of its own. `command_lifecycle` with `command_uuid` equal to the prompt's `uuid` says `queued` as soon as it arrives (the signal that it is waiting) and `started` when its turn begins; the `isReplay` echo of it comes at that point, after `init`. `user_message_uuid`/`user_message_uuids` on the first frames of a reply name the prompt it answers.
- An interrupt gets a success response, then an `assistant` message with `aborted: true` holding what was streamed, a synthetic `user` message `[Request interrupted by user]`, the stream's closing events, and a `result` with `subtype: "error_during_execution"` and `is_error: true`.
- A denied permission request comes back as a `tool_result` with `is_error: true` and the denial's message, and Claude may try again within the same turn (two asks in one turn).
- `ExitPlanMode` and `AskUserQuestion` are ordinary `can_use_tool` requests; an `AskUserQuestion` answer reaches the tool as `input.answers`.
- `terminal_slash_commands` and `plugins` are on `system/init` only; the `initialize` reply has `commands`.

**Re-recording.** Only the owner does this, by hand, never in CI: it runs the real `claude` on the owner's login and spends a few short Haiku turns (cents).

1. `node scripts/record-fake-claude.ts record <out-dir>` runs the SDK against `scripts/tee-claude.mjs`, which runs the real `claude` (`~/.local/bin/claude`, or the path given after `<out-dir>`) and copies every line each way into `<out-dir>/<scenario>.jsonl`: the scenarios are `text`, `permission`, `ask-question`, `plan`, `mid-turn` and `clear` (name some after the path to record only those). Denied asks mean nothing runs; the work folder is a throwaway inside `<out-dir>`, which belongs outside the repository (or in the ignored `.scratch/`, as in `.scratch/fake-claude-recording`).
2. `node scripts/record-fake-claude.ts fixtures <out-dir>` picks the example of each kind, replaces what identifies the recorder (the account becomes `you@example.com`, folders become `/home/you/...`, plugins, skills, MCP servers, agents and the recorder's own slash commands are emptied, signatures and rate-limit figures are made up) and rewrites `messages.json`. It refuses to write if the user name, home folder or `<out-dir>` is still in the output.
3. Read the diff of `messages.json` for anything personal, run `pnpm exec vitest run test/fake-claude-sdk.test.ts` and the tests that use the fake, and commit it with the SDK version it was recorded through.

## Seam 2: the browser (Playwright)

Specs live in `e2e/`.

- `e2e/harness.ts` exports `test` and `expect`. Its `kbench` fixture boots an isolated server in-process (temp data folder, unique `kb-test-*` tmux socket, random free port, so `kbench.stopServer()` and `kbench.startServer()` can restart it at the same address) serving `dist/web`, and sets the `Tailscale-User-Login` header on the browser context.
- The `app` fixture is an `AppPage` already open on the app (`otherDevice` is a second one in another browser context), with helpers that find things by role and accessible name: `createWorkspace()`, `createSession()` (a shell, through the New Session dialog), `createClaudeSession()` (a Claude TUI through the dialog; it takes a name and the Launch options by the label of the choice, such as `{ model: "Opus", effort: "XHigh", focusView: true }`), and for the steps `openNewSessionDialog()`, `createInDialog()` (name, kind `"Shell"` or `"Claude TUI"`, options, then Create), `newSessionDialog` and `newSessionKinds`, `claudeGlyph()`, `session()`, `sessionStatus()`, `sessionMenu()`, `terminal()`, `runMarker()`, `runCommand()`, `terminalSize()`.
- `kbench.openAgent(sessionName)` opens a Claude Agent's socket as a device would (a Seam 1 `AgentClient`, with the login header), to send prompts, such as a long conversation, with no browser involved.
- Claude Code is the same stub as in Seam 1 (the `kbench` instance is a `createTestInstance()`), so a Claude Session's terminal shows the stub's lines.
- Playwright has three projects: `desktop` (1280x800, every spec except `phone.spec.ts` and `smart-typing.spec.ts`), `phone` (a Pixel 7: touch, 412px wide, runs only `e2e/phone.spec.ts`) and `iphone` (WebKit with Playwright's iPhone 15 settings: touch, an iPhone user agent, 393px wide, runs only `e2e/smart-typing.spec.ts`). `AppPage` has `openDrawer()`, `drawer` and `extraKey(name)` for the phone project, whose sidebar is hidden until the drawer is open.
- Smart typing is offered only on an iPhone in the phone layout, so `e2e/smart-typing.spec.ts` runs on the `iphone` project. Playwright cannot drive the real iOS keyboard, so a test makes the keyboard's edits itself on the terminal's hidden field (`keyboardEdit()` in the spec: it selects a range in the field and runs `document.execCommand("insertText")` or `"delete"` over it, which raise real `beforeinput` and `input` events). It asserts what the Session's program received by running `cat -vet` on a terminal in raw mode (`stty raw -echo opost onlcr`), which prints Enter as `^M`, Backspace as `^?` and a line feed as `$`, with no line discipline between the keyboard and `cat` to erase, echo or translate anything. Keep what a test sends short: a long line wraps in the narrow terminal and splits the text the test looks for. The hidden field is the textbox named "Terminal input"; its keyboard settings (`autocorrect`, `autocapitalize`, `spellcheck`) are what iOS reads, so tests assert on them as attributes. A freshly cleared field is not empty but holds the filler (U+200B), so assert with a pattern built from the spec's `ZWSP` constant (a `RegExp` of `^${ZWSP}*$`), and `keyboardEdit()` counts its range after the filler.
- A Claude Agent in Seam 2 runs the real Agent Runtime against the fake `claude` (see [Claude Agents](#claude-agents)); `AppPage` has `createClaudeAgent()` (through the New Session dialog), `agentRegion(name)` (the Pane's region, `Claude Agent <name>`, where a terminal is `terminal(name)`), `agentInput(name)`, `agentModeLine(name)` (the permission mode line, a button) and `permissionPrompt(name)` (the permission panel that replaces the input while Claude waits on an ask). The phone's Claude Agent test lives in `phone.spec.ts`, because only the `phone` project runs it.
- To add a test, write `e2e/<topic>.spec.ts`, import `test`/`expect` from `./harness.ts`, and add any new UI helper to `AppPage`. Use `kbench.instance.makeFolder()` for Workspace folders.

## Seam 3: the packed `k-bench` command (Vitest)

`test/packed-command.test.ts` tests what a stranger gets from `npm i -g @k-electron/k-bench`: the real package, run as a process. Its harness is `test/harness/packed.ts`.

- `packedPackage()` runs `pnpm build` (with `NODE_ENV=production`, since Vitest sets `test`), `npm pack`, and installs the tarball into a temp prefix with `npm install --global --prefix <tmp>`. Never the real prefix. It runs once per test process, fetches the package's dependencies from the npm registry (so it needs the network, and the npm cache makes repeats fast) and returns the installed package folder, its `k-bench` bin and its version. Call it in a `beforeAll` with a long timeout; tests that use it should share one file, because each test file packs again.
- `new Stubs(options)` makes a folder of stub programs, written as plain `sh` so they run under the bash 3.2 of the CI runner. `runKBench(pkg, args, { stubs })` runs the packed command with `PATH` set to that folder plus `/usr/bin:/bin` and nothing else, and `HOME` set to a fresh empty folder (it returns it as `result.home`), so the command can reach neither the real machine nor a real tmux or Tailscale.
  - `tmux: false`, `tailscale: false` or `launchctl: false` leave that program off PATH (a Mac with the Tailscale app still has its CLI at the fallback path inside `/Applications/Tailscale.app`, which the installer also finds). The folder also holds a `node` link, so the bin's `#!/usr/bin/env node` still works.
  - `tailscale` answers `status --json` and `serve status --json` from files. Set them per test with `new Stubs({ tailscale: { status, serveStatus } })`, or change them later with `stubs.setStatus(...)` and `stubs.setServeStatus(...)`; pass an object (stringified) or a string. The defaults are a logged-in node and an empty serve config. Any other `tailscale` invocation is a change to the tailnet and is recorded: `stubs.tailscaleWrites()` lists them, which is how a test checks that a dry run, or a refusal, changed nothing.
  - `serveStatusOf([443, "http://127.0.0.1:3000"], ...)` builds a serve configuration in the shape Tailscale prints (one web entry per `[port, proxy]`, under the host `STUB_DNS_NAME`). The stub does not apply writes to it: nothing in this seam runs a real install, which is the only thing that writes, so a test sets the configuration it needs up front.
  - `launchctl: { loaded: true }` makes `launchctl print` succeed; every call is recorded in `stubs.launchctlCalls()`. The stub `tmux` records every call in `stubs.tmuxCalls()` and always succeeds.
- `startPackedServer(pkg, login, env?)` (`test/harness/packed-server.ts`) starts the packed package's real server on a free port with a throwaway data folder and tmux socket, admitting only `login` (`env` adds to its environment), and returns `{ port, stop() }`; `stop()` also ends the tmux server it may have started. A test that starts Agents sets `K_BENCH_CLAUDE_PROGRAM` to `installFakeClaude(packedTempDir())` (an absolute path, which `resolveConfig` reads for tests only: a `claude` first on PATH could lose to the owner's real one after the login shell's path setup), and a `HOME` and `ZDOTDIR` of its own. It is how `k-bench status` gets a real health endpoint to ask: the status tests run the command with `K_BENCH_STATUS_PORT` set to that port (the stub serve configuration proxies to it too) and a `HOME` holding a fake `Library/Application Support/k-bench/app/build-info.json`. Stop the server in an `afterEach`.
- To add a case, add a test to `test/packed-command.test.ts`, build the `Stubs` it needs and assert on the exit status, stdout, stderr, the files left in `result.home` and the recorded calls. If a command needs a new stub behaviour, add an option to `Stubs` rather than writing a one-off script in the test.
- Covered: the packed package runs at all (`--version`, so compiled JavaScript with nothing missing), its server starts from the installed package and serves the built front end with the version in the startup line, `install --dry-run` describes the install, ends with the URL and changes nothing, a missing tmux or a Node older than 26 (`new Stubs({ nodeVersion })`) fails clearly, and an HTTPS port already serving something else stops the install (naming `--https-port` and `--force`) unless `--force`, another `--https-port` or k-bench's own entry (on any of two ports k-bench is published on) says otherwise. `uninstall --dry-run` and `--purge --dry-run` describe what they remove and keep, and work when nothing is installed; a real `uninstall` and `uninstall --purge` against stubs and a temp HOME remove the service, only k-bench's own serve entry and the app folder, keep the data, and (purge) end the tmux server and delete the data; with k-bench published on two ports, uninstall removes both entries and leaves a foreign one. The real install and uninstall, which load a LaunchAgent and change the tailnet, are not run: see the [manual checklist](install-verification.md).

## The release tooling

`test/release.test.ts` runs `scripts/release.ts` as a process against throwaway repositories (a bare "origin" on disk, so no network, and a stub `gh` first on PATH that records its arguments), and `scripts/release-plan.ts`, the release workflow's decision step, against a stub npm registry on localhost. The workflow file itself is proved by its manual dry run: see [Releasing](releasing.md).

## The installer and a built server

The install changes the real system, so only its pure parts are unit-tested (`test/install.test.ts`), plus the packed command's dry run (Seam 3); the rest is the [manual checklist](install-verification.md). To try a production build by hand without installing it, run `pnpm smoke` (add `--hold` to keep it up for manual requests); everything it starts is cleaned up when it exits. See [Packaging](packaging.md) for how the package is built.
